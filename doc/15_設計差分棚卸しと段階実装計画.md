# SeedShiftRadio 設計差分棚卸しと段階実装計画

## 1. 目的

本書は `doc/00` から `doc/14` を現行実装へ突き合わせ、`実装済み`, `部分実装`, `未着手` を整理し、残差分を実装タスクへ分解するための作業メモである。

前提:

- 現状の主実装は Spring Boot サーバーであり、`/web` は未作成、`workers/musicgen` は deterministic worker まで実装済み
- 調査起点は `radio`, `settings`, `monitor`, `stream`, `letter`, `programming`, migration, test 一式
- 2026-03-29 時点の棚卸し結果を記録する

## 2. ステータス凡例

- `実装済み`: 設計意図と現行コードが概ね一致
- `部分実装`: 骨格はあるが、永続化・契約・外部連携・試験の一部が不足
- `未着手`: 実装ディレクトリや主要経路がまだ存在しない

## 4. 今回埋めた差分

### 4.1 settings / persistence / asset

- `schemaVersion` を `String` 契約へ統一
- `features.streaming.placeholderEnabled` を `config.json` 契約へ反映
- `generated_asset`, `provider_job`, `play_history`, `queue_item.asset_id` を Flyway と JPA へ追加
- `/api/assets/audio/{assetId}.wav` が `generated_asset.storage_path` を優先して返すように修正

### 4.2 non-blocking job 基盤

- `WarmupQueueJob`, `QueueRefillJob`, `GenerateMusicJob` を明示クラス化
- `GenerateMusicJob` は worker 未接続時の placeholder asset 生成で queue を前進可能にした
- `provider_job` と `generated_asset` を queue item に紐付けて追跡可能にした

### 4.3 programming runtime profile

- `station_programming_policy` に `pre_generation_policy`, `replay_policy`, `composition_policy` を追加し、設計書どおり JSONB で保持するようにした
- `GET/PUT /api/stations/{id}/programming` が runtime profile を含む完全版の編集用文書を返すようにした
- `GET /api/stations/{id}` の `programming` 要約にも runtime profile を含め、Station detail との契約差分を解消した

### 4.4 MusicGen worker 契約の実装

- `workers/musicgen` に FastAPI worker を追加し、`POST /music/jobs`, `GET /music/jobs/{id}`, `GET /health` を実装
- Spring Boot 側に `MusicGenWorkerGateway`, `MusicGenerationRuntimeService` を追加し、`submit -> poll -> generated_asset 登録 -> queue READY` を実装
- MusicGen 入力が一致する場合は `generated_asset.cache_key` から既存音源を再利用し、worker 再呼び出しを避けるようにした
- worker 失敗時は `provider_job.error_code` を保持しつつ `DEGRADED` + queue refill へ進めるようにした
- `generated_asset.queue_item_id`, `generated_asset.provider_job_id` を JPA でも保持するようにした

### 4.5 履歴/レター採用追跡 API

- `GET /api/play-history`, `GET /api/play-history/{id}` を追加し、`sessionId`, `stationId`, `letterId`, `resultStatus` で放送履歴を参照可能にした
- `GET /api/letters/{id}` を追加し、本文、返信、放送履歴をまとめて返せるようにした
- `LETTER` queue 生成時に採用済みレターを `queue_item.letter_id` へ束縛し、`play_history.letter_id` へ引き継ぐようにした
- `LetterSegmentBinderTests` と `RadioApiTests` で採用済みレターの履歴追跡を検証した

### 4.3 test / CI

- `RadioApiTests` を `docker` tag 化
- Gradle に `dockerTest`, `ciTest` を追加
- GitHub Actions に local suite / docker suite の 2 job 雛形を追加

## 5. 残タスク詳細

### 5.1 Phase A: MusicGen worker 実接続

目的:

- `GenerateMusicJob` の placeholder 実装を本来の worker 契約へ置き換える
- `doc/09` の非同期 worker 契約を実体化する

実装タスク:

1. `workers/musicgen` に FastAPI プロジェクトを追加する
2. `POST /music/jobs` と `GET /music/jobs/{id}` を `doc/09` 契約で実装する
3. Server 側に MusicGen client を追加し、`provider_job.external_ref` に worker `jobId` を保持する
4. `GenerateMusicJob` を `submit -> poll -> generated_asset 作成 -> queue READY` へ差し替える
5. timeout / worker error 時は `provider_job.error_code` を更新し、`MUSIC_LOCAL` または `JINGLE` へ縮退させる
6. FastAPI contract test と Spring 側 integration test を追加する

2026-03-29 実装済み:

- 1, 2, 3, 4 は deterministic worker を用いる形で実装済み
- 5 は `DEGRADED` + queue refill 再要求まで実装済み。`MUSIC_LOCAL` 実音源や専用 jingle asset への切替は未実装

残作業:

- worker の内部生成器を実モデル adapter へ差し替える
- `MUSIC_LOCAL` / jingle 実音源への縮退を実装する
- FastAPI contract test と Spring 側 integration test を追加する
- cache retention / eviction と `config.json.cache` の実運用値反映を実装する

完了条件:

- `MUSIC_AI` item が placeholder ではなく worker 生成音源で `READY` へ遷移する
- worker 停止時も queue が無音停止せず縮退継続する

### 5.2 Phase B: Provider 抽象の実装

目的:

- `doc/07` の Provider abstraction を導入し、settings と runtime を結び付ける

実装タスク:

1. `ScriptProvider`, `TtsProvider`, `MusicProvider` interface を追加する
2. `ProviderRegistry` を作り、`config.json` の default/fallback provider を解決できるようにする
3. `SettingsService` と `ProviderHealthService` を provider registry ベースへ寄せる
4. `AssetService` の placeholder 直結を `TtsProvider` / `MusicProvider` 呼び出しへ置き換える
5. provider fingerprint, capability, timeout を settings から注入する
6. mock provider 実装と異常系 test を追加する
7. `StationProgrammingPolicy` の `preGeneration` / `replay` / `composition` を JSONB で永続化し、`GET/PUT /api/stations/{id}/programming` と `StationDetail` に完全版を反映する

完了条件:

- Provider 追加が service 差し替えだけで成立する
- `provider.health.changed` と `/api/settings/test-connections` が同じ registry を使う
- 番組編成ポリシーの runtime profile が UI / API で往復できる

### 5.3 Phase C: Web Client 実装

目的:

- `doc/03` の Web UI を `/web` として着手し、Server 契約の主要利用者を揃える

実装タスク:

1. `/web` に Next.js App Router, TypeScript, TanStack Query, Zustand, Tailwind の基盤を追加する
2. `/` にプレイヤー画面を実装し、`tune/play/stop/status/queue/program` を接続する
3. `/letters` に一覧、状態更新、採用導線を実装する
4. `/settings` に `/api/settings`, `/api/settings/test-connections` を使う管理画面を実装する
5. `/monitor` に `/api/monitor/summary`, `/api/health`, recent event 表示を実装する
6. SSE subscribe, `Last-Event-ID` 再接続, queue/program/status の反映を実装する
7. audio element 再生、fallback 表示、client capability 登録を実装する

完了条件:

- ブラウザから一連の tune -> play -> playback-events -> stop が通る
- SSE 再接続後も状態が破綻しない

### 5.4 Phase D: 履歴/レター採用追跡

目的:

- `doc/12` の「採用後に放送履歴で追える」状態を API と UI で実現する

実装タスク:

1. `/letters` と `/monitor` から新設した履歴 API を消費する UI を追加する
2. `SEGMENT_ERROR`, `STOPPED`, retune 停止時の結果差分を画面側でも見分けやすくする
3. 履歴一覧にキーワード検索やページングが必要なら追加する
4. 採用済みレターの自動 `REPLIED` 化や返信補助導線を検討する

完了条件:

- `ADOPTED` レターから放送実績が辿れる
- play history の結果種別が監視画面とレター画面の双方で使える

### 5.5 Phase E: QA / CI 仕上げ

目的:

- Web, worker を含めた回帰導線を `doc/11` 通りに揃える

実装タスク:

1. `Vitest` による Web の state/store test を追加する
2. `Playwright` で主要画面の E2E を追加する
3. FastAPI worker の contract test と health test を追加する
4. GitHub Actions に Web / worker job を追加し、`ciTest` と役割分担する
5. observability 観点として `play_history`, provider health, queue warning の検証を追加する

完了条件:

- Server 単体, Docker integration, Web E2E, worker contract が CI で分離実行される
- 失敗時にどの層が壊れたかが workflow 名で判別できる

## 6. 推奨実装順

1. Phase A を先に進め、`MUSIC_AI` の placeholder を本接続へ寄せる
2. Phase B で provider abstraction を揃え、Server 側の実装方針を固定する
3. Phase D を Server API として先に整え、履歴契約を確定する
4. Phase C で `/web` を実装し、確定済み API 契約を消費させる
5. Phase E で Web/worker を含む QA と CI を完成させる
