# AIローカルラジオアプリ 運用・監視・セキュリティ・テスト設計書

## 1. 目的

本書は非機能要件、監視、運用、セキュリティ、プライバシー、試験方針を一つにまとめた実装補助文書である。

## 2. 非機能目標

| 項目 | 目標 |
|---|---|
| Tune から再生開始 | 5 秒以内 |
| 通常時 Ready 件数 | 2 件以上 |
| Music Generation / ACE-Step 失敗時 | 再生停止しない |
| 再起動後の設定/履歴保持 | 維持されること |
| 同時接続 | 3 から 5 クライアント程度 |
| ローカル復旧目標 RTO | 15 分以内 |

## 3. 監視

### 3.1 推奨OSS

- Spring Actuator
- Micrometer
- Prometheus
- Grafana
- logstash-logback-encoder

### 3.2 主要メトリクス

- queue ready count
- queue ready duration
- active program block count
- program planning latency
- program planning fallback count
- provider response time
- provider error count
- music job running count
- ACE-Step queue size, queued/running jobs, average job seconds
- ACE-Step model list / default model availability
- cache hit rate
- cache bytes by type
- cache eviction count
- asset consistency issue count
- prepared duration
- prepared block count
- archive replay rate
- archive pool size
- disk free space
- provider health status (UP/DEGRADED/DOWN) by type, `lastCheckedAt`, `responseTimeMs`, `message`, `capabilities`

`provider.health.changed` SSE を通じて `ProviderHealthPayload` を再配信し、監視 UI は Last-Event-ID で切断再接続に対処する。`/api/monitor/summary` と `/api/health` も同 Payload を含むため、Dashboard で同じ情報を再利用できる。

`/api/monitor/summary` は READY queue の `queueReadyDurationMs`、generated asset cache の `assetCount`, `byteSize`, `cacheHitCount`, `cacheHitRate`, `expiredAssetCount`, 種別別内訳、archive の `eligibleArchiveCount`, `totalArchiveCount`, `archiveReplayCount`, `totalPlaybackCount`, `archiveReplayRate` も返す。値は DB メタデータと履歴から集約し、prompt / lyrics / letter body / radioName は含めない。

## 4. ログと監査

- 構造化 JSON ログを標準とする
- `correlationId`, `stationId`, `sessionId`, `queueItemId` を出す
- 可能なら `programBlockId`, `programTemplateId`, `programSlotId` も出す
- 設定変更、局切替、局設定変更、番組テンプレート変更、レター状態変更、縮退遷移を監査対象にする
- レター本文全文、プロンプト全文、歌詞全文、radioName、API key、管理トークン、Provider 応答本文は標準ログへ出さない
- 音楽生成では `promptHash` / `lyricsHash` と短い label のみを監査・SSE・API response に出す

## 5. Runbook 最低項目

- Provider 停止時の切り分け
- Queue が詰まった時の再生成手順
- 先行生成 backlog が積み上がった時の抑止手順
- 番組テンプレート不整合時の fallback 確認手順
- ディスク不足時の古いキャッシュ削除手順
- station ごとの replay 強度と cache 上限の調整手順
- MusicGen Worker / ACE-Step 停止時の縮退運転
- ACE-Step `401`, `429`, `500`, timeout の分類確認
- XL profile unavailable 時に `ace-ja-fast` または既存 cache へ戻す手順
- PostgreSQL 障害時の復旧確認

generated asset の eviction job は `seedshift.radio.cache.eviction.enabled` と `seedshift.radio.cache.eviction.cron` で制御する。既定は有効で、`config.json.cache.cleanupBatchSize` 件を上限に期限切れ payload と種別別 size cap 超過分を処理する。参照整合性維持のため `generated_asset` record は削除せず、payload file を削除して cache key を外す。

generated asset の整合性検査は `GET /api/monitor/assets/consistency` を管理トークン付きで手動実行する。検査は read-only で、DB metadata と payload file の missing / byte size mismatch / content hash mismatch / orphan file / unreadable file を数える。`byteSize=0` の eviction 済み record は missing 扱いしない。Runbook ではこの API の issue count を確認し、orphan file の削除や DB metadata 修復は別手順として扱う。API response とログには raw metadata、prompt、lyrics、letter body、radioName、秘密値、絶対パスを出さない。

## 6. バックアップ

対象:

- `config.json`
- PostgreSQL dump
- 読み辞書
- 生成資産メタデータ
- 手動編集した局設定
- 番組テンプレートと編成ルール

生成音声・生成音楽の実ファイルは再生成可能なものを除き、毎日フルバックアップ対象にしない。

- ただし `broadcast_archive` に昇格し再放送正本として使う asset は、通常 cache と分けて保持期間とバックアップ方針を明文化する
- `/settings` の Export JSON は運用バックアップ補助として扱い、`configPath` や `updatedAt` は含めない。Import は server 上の raw file path を信頼せず、既存 `/api/settings` の保存検証を通して現在の `config.json` へ反映する。

## 7. セキュリティ

- bind host は既定で `127.0.0.1`
- 管理系 API は `X-Admin-Token` を要求する
- CORS は same-origin を基本とする
- レター入力は prompt injection 前提で扱う
- 番組テンプレートに含まれる prompt 補助文もログへ全文を残さない
- `/settings` Import / Export では `apiKeyRef` と `adminTokenRef` を `env:` / `file:` 参照に限定し、管理トークンや API key の実値を JSON に含めない
- ファイルパスは許可済みルート以外を参照させない
- CLI 連携は Java 本体から直接実行せず worker 経由とする
- ACE-Step API key は `apiKeyRef` で `env:` / `file:` 参照として解決し、設定画面にも実値は表示しない
- prompt / lyrics / letter body は untrusted input とみなし、歌詞には直接混ぜず安全なテーマへ抽象化する

## 8. プライバシー

- `radioName`, letter body, 放送履歴は個人データ相当として扱う
- 画面・ログ・監視へそのまま露出しない
- 保持期間と削除方針を明文化する
- プロンプトへ個人情報を混ぜる場合は必要最小限に限定する

## 9. OSS/モデル/音源ライセンス管理

最低でも以下を台帳管理する。

- OSS 名称
- バージョン
- ライセンス
- 再配布義務
- モデル利用条件
- 生成物の利用条件

特に TTS モデル、音声モデル、音楽生成モデルは本体 OSS と別条件のことがあるため分けて管理する。

## 10. テスト戦略

### 10.1 サーバー

- `JUnit 5`
- `Testcontainers`
- Docker 不在のローカル環境でも `ProgramRule` 判定、`LetterService` の冪等投稿と状態遷移、`Last-Event-ID` 再送は単体 test で確認できるようにする
- `WarmupQueueJob` / `QueueRefillJob` は background job server 無効時に after-commit のインライン実行へ切り替え、service test で `PREPARING` 応答と queue 補充を再現できるようにする
- `GenerateMusicJob` は worker 未接続時でも placeholder asset を返す mock 経路を持ち、queue の縮退継続を service test で確認する
- `PromoteArchiveCandidateJob` は `play_history` 保存後の after-commit job とし、promotion 失敗や二重実行で playback event / 履歴保存が壊れないことを unit test で確認する
- ACE-Step adapter は request mapping、`query_result` parse、audio download、HTTP 401/429/500/timeout 分類を unit / contract test で確認する
- 日本語歌詞 30-60 秒、インスト、長め 120 秒、XL profile unavailable、ACE-Step 停止中の 5 ケースで radio playback が継続することを manual acceptance とする
- cache hit, archive replay, station `replayPolicy`, `compositionPolicy` の組み合わせを service test で確認する
- `QueuePreparationPolicy` は `REALTIME_ONLY` の最小 buffer、station `maxPreparedMinutes` / `maxPreparedBlocks` の global cap clamp、`idlePrefetchEnabled` による ahead count 補正を unit test で確認し、`RadioService` 側の orchestration 回帰とは分離して押さえる
- `preGeneration.mode=REALTIME_ONLY` では最小 buffer を維持しつつ次 block の先行計画を抑制し、station `maxPreparedMinutes` / `maxPreparedBlocks` が global `playout` cap を超えないことを service test で確認する
- `preGeneration.preferCacheReuse=false` のとき、reusable MusicGen asset が存在しても `CACHE_REUSED` へ寄らず worker submit を優先し、`true` または policy 未設定時の cache-first 挙動は維持されることを service test で確認する
- `musicAheadCount` は `MUSIC_AI` の同時生成深さだけを制御し、`READY` 件数・`READY` duration・`REALTIME_ONLY` の next block 抑制・`CACHE_REUSED` / `LIVE_GEN` の意味を変えないことを service test で確認する
- `scriptAheadCount` / `ttsAheadCount` は future spoken queue item の script/TTS 生成深さだけを制御し、`READY` 件数・`READY` duration・`resumePlayback` の初音保証・`REALTIME_ONLY` の next block 抑制を壊さないことを service test で確認する
- `ttsAheadCount=0` でも次に再生される spoken item 1 件ぶんの audio 生成は維持し、ahead window の進行で後続 spoken item の audio/script prefetch が前進することを service test で確認する
- `idlePrefetchEnabled=false` のとき、manual play 待機中は `minimumReadyCount` / `minReadyDurationMs` 達成後の extra prefetch を最小化しつつ、active playback 中の refill と `resumePlayback=true` の auto-start は維持されることを service test で確認する
- `composition.allowSoftFallbackRetiming=false` のとき、`SOFT` slot でも letter 優先、talk 連続回避、music break 優先の再配置が走らず、candidate / fallback の通常解決順を維持することを service test で確認する
- `composition.targetSegmentShares` は `SOFT` slot の `candidateSegmentTypes` の範囲だけで候補選択を変え、share 目標のために fallback を強制しないことを service test で確認する
- archive replay は block 単位 `maxReplaySharePercent` の上限制御、quota 超過時の `LIVE_GEN` 継続、`cooldownHours` と両立した候補選定を service test で確認する
- generated asset consistency は `byteSize=0` eviction record を正常扱いにしつつ、missing file、byte size mismatch、content hash mismatch、orphan file を service / MockMvc test で確認する
- Gradle は `test` を Docker 不要 suite、`dockerTest` を Testcontainers suite として分割し、CI では両方を回す
- `SpringBootTest` の smoke / API test は `docker` tag を明示し、Testcontainers suite 側へ寄せる
- `SpringBootTest` の API test は test 専用 `config.json` をクラスごとに分離し、provider health probe の待機を最小化する
- Provider mock を使った service test
- Queue / Fallback の状態遷移 test
- ProgramRule 解決、ProgramBlock 版固定、Preview 検証 test

### 10.2 Web UI

- `Vitest`
- `Playwright`
- `/settings` Import / Export は Vitest で export metadata 除外、schemaVersion mismatch、Import/Export 双方の secret 参照検証、未登録 fallback provider の拒否を確認する
- `/settings` station 基本情報 editor は API client test で `PUT /api/stations/{id}` の管理トークン、JSON body、URL encode を確認する。Playwright では blank create、duplicate draft、保存後の新 station 選択、station policy を持ち込まないこと、dirty draft の破棄確認を確認する
- `/settings` station programming policy editor は API client test で `PUT /api/stations/{id}/programming` の管理トークン、JSON body、URL encode を確認し、Playwright では既存 station の `planningHorizonMinutes` 更新と保存 notice を確認する
- `/settings` programming preview は API client / service test で `POST /api/stations/{id}/programming/preview` の管理トークン、JSON body、未保存 `policyDraft` / `templateDraft` の request 反映、persisted policy 未作成時の既定 template 解決、inactive template 非選択、slot fallback 時の `fallbackApplied` / warning を確認し、Playwright では未保存 draft を含む preview request と結果表示を確認する
- `/settings` ProgramTemplate editor は API client test で `POST/PUT /api/program-templates` の管理トークン、JSON body、URL encode を確認し、Vitest では blank/duplicate draft と JSON object serialize、`ApiRequestError` の field error 取り込みを確認する。Playwright では blank create の必須入力、保存後の新 template 選択、duplicate draft open/close、existing template edit、slot add、save に加え、create/update の `400` / `409` で message / field error を表示しつつ draft を保持することを確認する
- `ProgrammingService` の service test では provider health 由来 fallback に加え、`composition.maxConsecutiveTalkSegments`, `composition.musicBreakIntervalMinutes`, `composition.letterPriorityBoostThreshold` が runtime の `ResolvedSlot` 列へ反映されることを確認する
- `Vitest` では `ui-store` の persist / LocalStorage 連携、`api.ts` の header / query / error parse / 204 応答、`monitor-provider-health.ts` の metadata 正規化、`safe-metadata.ts` の secret / prompt / lyrics / letter body / radioName redaction を `jsdom` と fetch/env mock 前提で確認する
- Provider health / monitor 表示は Web 側でも契約違反 payload を直接描画しない。`metadata`, `message`, `baseUrl`, `externalRef`, audit `summary` に秘密値や本文らしい key-value / credential URL が含まれる場合は `[redacted]` に置き換える。
- `Playwright` では `/` の `Tune -> Play -> audio playback event`、`/letters` の `投稿 -> ローカル履歴 -> 公開採用履歴`、SSE の `subtitle.updated` と reconnect 時 `Last-Event-ID` 再送を mock API / mock stream / audio stub で確認する
- SSE reconnect は内部 route `/stream-harness` 上で `openSeedShiftStream` を直接使い、通常画面の `LiveStreamBridge` とは独立に `initialLastEventId` 再送を確認する
- E2E は headless Chromium を標準とし、`page.route` で `127.0.0.1:8080` の REST / SSE を差し替え、実音声ファイルや実 Server 起動を必須にしない
- 局管理、番組テンプレート編集、Preview 実行の E2E
