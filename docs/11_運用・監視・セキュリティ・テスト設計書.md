# AIローカルラジオアプリ 運用・監視・セキュリティ・テスト設計書

## 1. 目的

本書は非機能要件、監視、運用、セキュリティ、プライバシー、試験方針を一つにまとめた実装補助文書である。

## 2. 非機能目標

| 項目 | 目標 |
|---|---|
| Tune から再生開始 | 5 秒以内 |
| 通常時 Ready 件数 | 2 件以上 |
| Music Generation / ACE-Step 失敗時 | 再生停止しない |
| Irodori-TTS 失敗時 | VOICEVOX または既存 TTS cache へ縮退し、再生停止しない |
| 再起動後の設定/履歴保持 | 維持されること |
| 同時接続 | 3 から 5 クライアント程度 |
| ローカル復旧目標 RTO | 15 分以内 |

## 3. 監視

### 3.1 推奨OSS

- Spring Actuator
- Micrometer
- Prometheus
- Grafana
- logstash-logback-encoder

### 3.2 主要メトリクス

- queue ready count
- queue ready duration
- active program block count
- program planning latency
- program planning fallback count
- provider response time
- provider error count
- LLM adapter / model ごとの response time、error code、fallback count
- music job running count
- ACE-Step queue size, queued/running jobs, average job seconds
- ACE-Step model list / default model availability
- Irodori-TTS health, model id, response format, synthesis queue wait, max concurrent synthesis, 503 count
- Irodori-TTS voice reference status count: ready / missing / consent required
- cache hit rate
- cache bytes by type
- cache eviction count
- asset consistency issue count
- prepared duration
- prepared block count
- archive replay rate
- archive pool size
- disk free space
- provider health status (UP/DEGRADED/DOWN) by type, `lastCheckedAt`, `responseTimeMs`, `message`, `capabilities`
- stale provider job recovery count (`seedshift.provider.jobs.recovered`)
- provider job recovery failure count (`seedshift.provider.jobs.recovery.failures`)

`provider.health.changed` SSE を通じて `ProviderHealthPayload` を再配信し、監視 UI は Last-Event-ID で切断再接続に対処する。`/api/monitor/summary` と `/api/health` も同 Payload を含むため、Dashboard で同じ情報を再利用できる。

`/api/monitor/summary` は READY queue の `queueReadyDurationMs`、generated asset cache の `assetCount`, `byteSize`, `cacheHitCount`, `cacheHitRate`, `expiredAssetCount`, 種別別内訳、archive の `eligibleArchiveCount`, `totalArchiveCount`, `archiveReplayCount`, `totalPlaybackCount`, `archiveReplayRate` も返す。値は DB メタデータと履歴から集約し、prompt / lyrics / letter body / radioName は含めない。

`ProviderJobRecoveryJob` は `seedshift.radio.provider-job.recovery.enabled=true` を既定とし、`seedshift.radio.provider-job.recovery.stale-after=15m`, `seedshift.radio.provider-job.recovery.fixed-delay=60s`, `seedshift.radio.provider-job.recovery.batch-size=100` を起動プロパティで調整できる。
`stale-after` は正の Duration を必須とし、`batch-size` は 1 から 1000 の範囲へ補正する。
`RUNNING` かつ `updated_at < now - stale-after` の job を 1 回最大 batch 件まで条件付き更新し、`FAILED / PROVIDER_INTERRUPTED`、`ended_at=回収時刻` へ確定する。
残件は次回周期へ持ち越し、同時実行や再走では既に状態が変わった job を更新しない。
回収済み job は既存 `/api/monitor/summary` の `runningJobs` から外れ、`recentErrors` に現れるため、専用 DTO は追加しない。
失敗確定時は既存 `provider.job.failed` を safe metadata だけで配信する。
Micrometer counter `seedshift.provider.jobs.recovered` は条件付き更新に成功した件数、`seedshift.provider.jobs.recovery.failures` は定期回収処理が例外終了した回数を累積する。
`runOnce` の `checkedAt`, `cutoff`, `scannedCount`, `recoveredCount` は内部の test / 運用確認に使い、公開監視はこれらの counter と既存 summary / event の状態遷移を利用する。
`PROVIDER_INTERRUPTED` は自動 fallback / 再送不可であり、request 本文を `provider_job` に保存しない契約を維持するため、cleanup job 自身は再投入しない。
再生継続は queue warmup / refill / planning が cache や placeholder、または新規論理要求で補充する責務とする。

## 4. ログと監査

- 構造化 JSON ログを標準とする
- `correlationId`, `stationId`, `sessionId`, `queueItemId` を出す
- 可能なら `programBlockId`, `programTemplateId`, `programSlotId` も出す
- 設定変更、局切替、局設定変更、番組テンプレート変更、レター状態変更、縮退遷移を監査対象にする
- レター本文全文、プロンプト全文、歌詞全文、radioName、API key、管理トークン、Provider 応答本文は標準ログへ出さない
- 音楽生成では `promptHash` / `lyricsHash` と短い label のみを監査・SSE・API response に出す

現行 Server では Spring Boot の structured logging を使い、既定の console log は Logstash JSON 形式とする。`SEEDSHIFT_RADIO_LOG_FORMAT` で console format を、`SEEDSHIFT_RADIO_FILE_LOG_FORMAT` と `SEEDSHIFT_RADIO_LOG_FILE` で file log 出力先を切り替えられる。

`CorrelationIdFilter` は `X-Correlation-Id` を response へ返し、同じ値を MDC の `correlationId` に入れる。path segment または query parameter から安全に抽出できる場合だけ `stationId`, `sessionId`, `queueItemId`, `programBlockId` も MDC に入れ、request 完了時に `method`, `path`, `status`, `elapsedMs` を短い access log として出す。request body, query string, header, Provider 応答本文は access log に含めない。

## 5. Runbook 最低項目

- Provider 停止時の切り分け
- Ollama / OpenAI 互換 LLM の health、model 存在、認証参照、20 秒 timeout、定型 TALK fallback の確認
- Queue が詰まった時の再生成手順
- 先行生成 backlog が積み上がった時の抑止手順
- 番組テンプレート不整合時の fallback 確認手順
- ディスク不足時の古いキャッシュ削除手順
- station ごとの replay 強度と cache 上限の調整手順
- MusicGen Worker / ACE-Step 停止時の縮退運転
- Irodori-TTS 停止時の VOICEVOX fallback 確認
- Irodori-TTS 503 / queue timeout / model load timeout 時の `ttsAheadCount`, cache hit, fallback provider の確認
- 参照音声 missing / consent 未確認時に該当 VoiceProfile を外し、別 VoiceProfile か VOICEVOX へ戻す手順
- ACE-Step `401`, `429`, `500`, timeout の分類確認
- XL profile unavailable 時に `ace-ja-fast` または既存 cache へ戻す手順
- PostgreSQL 障害時の復旧確認

### 5.1 ローカル起動の標準手順

- `cp .env.example .env`
- `mkdir -p data/config data/library/music`
- `cp infra/compose/local-config.example.json data/config/config.json`
- `podman compose --env-file .env -f infra/compose/compose.yml up -d postgres musicgen`
- 必要時のみ `podman compose --env-file .env -f infra/compose/compose.yml --profile ai up -d ollama voicevox`
- repo root で `set -a && source ./.env && set +a && ./gradlew bootRun`
- `web` で `set -a && source ../.env && set +a && npm run dev`
- `http://127.0.0.1:3000/`, `/letters`, `/settings`, `/monitor` を開く
- `./scripts/smoke-local-stack.sh` で `worker/server/web` 疎通を確認する

ローカル標準では repo root を `server` とみなし、依存サービスだけを compose 管理する。初期 `config.json` は `infra/compose/local-config.example.json` を起点にし、MusicGen は `MUSICGEN_WORKER`、LLM は `Ollama`、TTS は `VOICEVOX` の localhost endpoint を前提にする。Irodori-TTS を使う場合は追加 profile として Irodori-TTS-Server を `127.0.0.1:8088` に bind し、承認済み参照音声 directory を `voices/` へ mount する。外部公開する場合は bearer token、firewall、上位 network ACL を必須にする。

### 5.2 GitLab CI/CD と Runner 前提

- GitLab CI/CD の正本は `.gitlab-ci.yml` とし、`iwaken-server` 上の Podman コンテナ版 GitLab Runner で実行する
- test 系 job は GitLab Runner `共有Test用Runner` を使い、`tags: [shared, shell]` を付ける
- deploy 系 job は GitLab Runner `podmanリリース用Runner` を使い、`tags: [shared, deploy]` を付ける
- GitLab 公式の SAST / IaC Scan / Secret Detection job は Docker executor の `iwaken-server-docker-executor-runner-18.8.0` を使い、`tags: [shared, docker]` を付ける
- どちらも `shell executor` 前提で、`image:` や `services:` には依存しない
- GitLab 公式 analyzer job は `/analyzer run` 前提のため shell executor へ流さず、job 名ごとに `tags` だけを上書きして Docker executor へ流す
- ただし `kics-iac-sast` は analyzer が `--output-path /tmp` を固定して SARIF を生成するため、`/tmp` へ書けない Docker executor では KICS CLI を直接呼び、`$CI_PROJECT_DIR/.tmp` に `glsast` を出力して `gl-sast-report.json` へ移動する
- Server のローカル build は JDK 21 以上を許容し、JDK 25 など新しい JDK の後方互換性を利用できるようにする。生成する class file と利用可能な Java API は Gradle の `options.release=21` で Java 21 に固定し、production / CI の JDK 21 互換を維持する
- test 系 job は runner host へ Java / Node.js / Python を直接要求せず、`podman --remote run` で JDK 21 / Node 22 / Python 3.12 / Playwright toolchain container を都度起動する
- container 操作は Docker ではなく `podman --remote` を使う
- KICS / Secret Detection analyzer が `/tmp` へ書けない runner 構成では、`TMPDIR`, `TMP`, `TEMP` を `"$CI_PROJECT_DIR/.tmp"` へ向け、job の `before_script` で当該 directory を作成する
- `server-docker` のような Testcontainers job は `podman --remote info` から取得した rootless Podman socket path と runtime dir をそのまま JDK container へ bind mount し、container 内では `XDG_RUNTIME_DIR`, `DOCKER_HOST=unix://<remote-socket>`, `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=<remote-socket>`, `TESTCONTAINERS_HOST_OVERRIDE=127.0.0.1`, `TESTCONTAINERS_RYUK_DISABLED=true` を前提にする。shell executor 側で `test -S` などのローカル socket 実在チェックは行わない
- `web-e2e` は Playwright 依存込みの toolchain container 上で動かし、CI では `PLAYWRIGHT_BROWSERS_PATH=0 npx playwright install chromium` と `npm run e2e` を同一 container 内で実行する
- GPU smoke は `podman --remote run --device nvidia.com/gpu=all --security-opt=label=disable ...` を使う
- deploy job は原則 `main` ブランチ限定かつ `manual` 実行とする
- 外部公開または本番相当の `stop` / `rm` / `restart` の前には、必ず `podman --remote ps` または `podman --remote inspect` を実行して対象確認を入れる
- `deploy-musicgen` はテスト実行向けに MusicGen worker を `0.0.0.0:28080` へ公開し、既定では生成物を container 内の一時データとして扱う。起動確認は runner container の `127.0.0.1` ではなく `podman --remote exec` で worker container 内の `/health` を確認する。外部到達を許可するため、runner host 側の firewall、ルーティング、上位 network ACL で許可元を絞り、必要なら `MUSICGEN_HOST_BIND` または `MUSICGEN_HOST_PORT` で bind 先と port を上書きする。永続化が必要な環境では、GitLab CI/CD Variables の `MUSICGEN_DATA_VOLUME` に Podman managed volume 名または絶対 host path を指定し、host path の場合は事前に directory、所有者、権限、backup 方針を準備する
- `server-container-build` / `web-container-build` は production image の build 可否を確認し、`server-container-publish` / `web-container-publish` は GitLab Container Registry へ commit SHA tag と branch tag を push する
- `deploy-migrate` は published Server image を `SPRING_MAIN_WEB_APPLICATION_TYPE=none`, `SEEDSHIFT_RADIO_MIGRATION_ONLY=true`, `SEEDSHIFT_RADIO_JOBRUNR_ENABLED=false`, `JOBRUNR_JOB_SCHEDULER_ENABLED=false` で起動し、既存 PostgreSQL へ Flyway migration を適用する。Spring 初期化と migration が成功したら ApplicationContext を正常終了する。失敗した場合は `deploy-app` へ進めない
- `deploy-app` は `infra/compose/compose.prod.yml` を deploy directory へ配置し、`podman --remote compose pull` と `podman --remote compose up -d` で Server / Web を更新する。deploy `.env` は `umask 077` で生成し、DB password や管理トークンを標準ログへ出さない
- Web は host network で `0.0.0.0:3000` を直接公開し、browser からの API/SSE は Next.js の `/api-proxy` Route Handler で `http://127.0.0.1:8080` の Server へ中継する。Server は標準で `127.0.0.1:8080` に bind し、CORS を広げない
- `smoke-production` は deploy 後に `GET /api/health`, Web `/`, Web proxy 経由 `/api/health`, `podman --remote ps` を確認する。失敗時のログ確認でも `radioName`, letter body, prompt, API key, 管理トークン, DB password は貼り付けない
- 詳細な stage、環境変数、rollback、初回デプロイ前チェックは [16_パイプライン・コンテナデプロイ仕様書.md](./16_パイプライン・コンテナデプロイ仕様書.md) を正本とする

### 5.3 非露出レビュー checklist

- `radioName`, letter body, prompt, lyrics, API key, 管理トークン, Provider 応答本文を標準ログへ出していない
- `subtitle.updated` や `provider.job.*` の summary は本文そのものではなく hash、件数、分類済み理由だけを出している
- `/api/monitor/summary`, `/api/health`, `/api/settings`, `/api/settings/test-connections` の response に raw secret や本文が含まれていない
- `settings` 保存時の `apiKeyRef`, `adminTokenRef` は `env:` または `file:` 参照だけを server / web の両側で受け付ける
- Web の provider health / monitor 表示は契約違反 payload が来ても `[redacted]` を優先し、そのまま描画しない
- worker 契約 test では `promptHash`, `lyricsHash` だけを固定し、本文を response に含めない

generated asset の eviction job は `seedshift.radio.cache.eviction.enabled` と `seedshift.radio.cache.eviction.cron` で制御する。既定は有効で、`config.json.cache.cleanupBatchSize` 件を上限に期限切れ payload と種別別 size cap 超過分を処理する。参照整合性維持のため `generated_asset` record は削除せず、payload file を削除して cache key を外す。

generated asset の整合性検査は `GET /api/monitor/assets/consistency` を管理トークン付きで手動実行する。検査は read-only で、DB metadata と payload file の missing / byte size mismatch / content hash mismatch / orphan file / unreadable file を数える。`byteSize=0` の eviction 済み record は missing 扱いしない。Runbook ではこの API の issue count を確認し、orphan file の削除や DB metadata 修復は別手順として扱う。API response とログには raw metadata、prompt、lyrics、letter body、radioName、秘密値、絶対パスを出さない。

## 6. バックアップ

対象:

- `config.json`
- PostgreSQL dump
- 読み辞書
- 生成資産メタデータ
- 手動編集した局設定
- 番組テンプレートと編成ルール

生成音声・生成音楽の実ファイルは再生成可能なものを除き、毎日フルバックアップ対象にしない。

- ただし `broadcast_archive` に昇格し再放送正本として使う asset は、通常 cache と分けて保持期間とバックアップ方針を明文化する
- `/settings` の Export JSON は運用バックアップ補助として扱い、`configPath` や `updatedAt` は含めない。Import は server 上の raw file path を信頼せず、既存 `/api/settings` の保存検証を通して現在の `config.json` へ反映する。

### 6.1 restore / cleanup の最小手順

- restore 前に `./scripts/smoke-local-stack.sh` または `GET /api/health` / `GET /api/monitor/summary` で現在状態を控える
- `config.json` を戻す時は raw file を直接編集し続けず、復元後に `/api/settings` の保存検証を 1 回通す
- PostgreSQL restore 後は `generated_asset` metadata と payload file の整合が崩れていないか `GET /api/monitor/assets/consistency` で確認する
- orphan file cleanup は `issueType=ORPHAN_FILE` を確認してから payload file だけを削除し、DB metadata は別手順で扱う
- cache cleanup 後は `/api/monitor/summary` の cache bytes, expired count, archive pool size が想定どおり減っているか確認する
- restore / cleanup の直後は `queue.updated`, `provider.health.changed`, `provider.job.*` に本文や秘密値が混ざっていないことも再確認する

## 7. セキュリティ

- bind host は既定で `127.0.0.1`
- 管理系 API は `X-Admin-Token` を要求する
- 管理トークンは起動プロパティ `seedshift.radio.security.admin-token` を優先し、未設定時は `config.json` の `security.adminTokenRef` を `env:` / `file:` 参照として解決する。どちらも未解決の場合、管理 API は `ADMIN_AUTH_REQUIRED` を返す。
- Web 管理 UI は管理トークンの実値を browser bundle、`NEXT_PUBLIC_*`、`localStorage`、Cookie、画面、SSE、標準ログへ渡さない。
- production では同一 origin の Next.js BFF が署名済み `HttpOnly`、`Secure`、`SameSite=Strict` session を確立し、CSRF 検証後に管理 API へ `SEEDSHIFT_ADMIN_TOKEN` を注入する。session 有効期間は 8 時間とする。
- Web ログイン資格情報 `SEEDSHIFT_WEB_ADMIN_PASSWORD` と Server 管理 API 用 `SEEDSHIFT_ADMIN_TOKEN` は分離する。session 署名には production で必須の `SEEDSHIFT_WEB_SESSION_SECRET` を使い、いずれも protected CI/CD Variable または権限制限した deploy env から渡す。
- BFF は browser request の `Cookie`、`X-Admin-Token`、`X-CSRF-Token` を upstream Server へ転送せず、管理対象として分類した API だけに server-side token を注入する。公開 API は session の有無にかかわらず token 非注入を維持する。
- `POST /api/auth/login` は同一 origin の request だけを受け付ける。`GET /api/auth/session` は認証状態と CSRF token だけを返し、状態変更を伴う管理 API proxy と `POST /api/auth/logout` は session に結び付く `X-CSRF-Token` を要求する。
- login の同一 origin 判定は、利用者から見える protocol と host を `Origin` と比較する。reverse proxy 配下では `X-Forwarded-Host` / `X-Forwarded-Proto` の先頭要素、直接接続では `Host` / request URL protocol を使い、Next.js 内部 URL の host には依存しない。公開経路の reverse proxy は外部から受けた forwarded header を除去または上書きし、`Origin` 欠落、不正 URL、protocol / host 不一致は fail-closed で拒否する。
- 管理 session Cookie の `Secure` 属性は公開 protocol が HTTPS の場合に有効化する。HTTPS reverse proxy は `X-Forwarded-Proto` を必ず上書きし、login と logout で同じ Cookie 属性を適用する。
- `NEXT_PUBLIC_SEEDSHIFT_ADMIN_TOKEN` と `NEXT_PUBLIC_ADMIN_TOKEN` は廃止し、Web build、browser storage、Cookie、画面、SSE、標準ログへ管理 API 用トークンを渡さない。
- CORS は same-origin を基本とする
- レター入力は prompt injection 前提で扱う
- 番組テンプレートに含まれる prompt 補助文もログへ全文を残さない
- `/settings` Import / Export では `apiKeyRef` と `adminTokenRef` を `env:` / `file:` 参照に限定し、管理トークンや API key の実値を JSON に含めない
- ファイルパスは許可済みルート以外を参照させない
- CLI 連携は Java 本体から直接実行せず worker 経由とする
- ACE-Step API key は `apiKeyRef` で `env:` / `file:` 参照として解決し、設定画面にも実値は表示しない
- Irodori-TTS-Server の optional API key も `apiKeyRef` で `env:` / `file:` 参照として解決し、設定画面、ログ、SSE、provider metadata に実値を出さない
- Web の現行 security baseline は Next.js `15.5.20` 以上、Vitest `3.2.7` 以上とし、Next.js 配下の PostCSS は `8.5.10` 以上、Vite は `6.4.3` 以上、`ws` は `8.21.0` 以上へ解決する
- Web 依存更新時と release 前に `npm audit` を実行し、production / development の既知脆弱性が 0 件であることを確認する
- prompt / lyrics / letter body は untrusted input とみなし、歌詞には直接混ぜず安全なテーマへ抽象化する
- 参照音声は本人または権利者の明示同意があるものだけを登録し、声優、著名人、実在個人の無断模倣、誤認を招く deepfake 的利用を禁止する
- Irodori の style emoji / control token は allowlist 変換のみ許可し、レター本文由来の絵文字や命令をそのまま制御 token として使わない

## 8. プライバシー

- `radioName`, letter body, 放送履歴は個人データ相当として扱う
- 画面・ログ・監視へそのまま露出しない
- 保持期間と削除方針を明文化する
- プロンプトへ個人情報を混ぜる場合は必要最小限に限定する

## 9. OSS/モデル/音源ライセンス管理

最低でも以下を台帳管理する。

- OSS 名称
- バージョン
- ライセンス
- 再配布義務
- モデル利用条件
- 生成物の利用条件

特に TTS モデル、音声モデル、音楽生成モデルは本体 OSS と別条件のことがあるため分けて管理する。

Irodori-TTS では最低限、`Irodori-TTS-500M-v3`, `Irodori-TTS-Server`, `Semantic-DACVAE-Japanese-32dim`, 参照音声ファイル、必要な LoRA adapter を別行で台帳管理する。model 本体が MIT license でも、model card の倫理的制約と参照音声の利用条件を運用条件として扱う。

Provider error code は共通で `PROVIDER_UNREACHABLE`, `PROVIDER_TIMEOUT`, `PROVIDER_BAD_RESPONSE`, `PROVIDER_REJECTED`, `PROVIDER_RESOURCE_EXHAUSTED`, `PROVIDER_AUTH_FAILED`, `PROVIDER_INTERRUPTED`、TTS 固有で `VOICE_REF_NOT_FOUND`, `VOICE_CONSENT_REQUIRED` を使う。

共通 acceptance test は次を固定する。

| Provider | 失敗条件 | 期待 error code | Provider chain / playout の期待結果 |
|---|---|---|---|
| LLM | timeout | `PROVIDER_TIMEOUT` | 設定された retry 上限後に次 Provider または安全な定型 TALK へ縮退する |
| LLM | unreachable | `PROVIDER_UNREACHABLE` | 次 Provider または安全な定型 TALK へ縮退し、放送を止めない |
| LLM | malformed / empty response | `PROVIDER_BAD_RESPONSE` | 次 Provider または安全な定型 TALK へ縮退する |
| LLM | safety block / request rejected | `PROVIDER_REJECTED` | 同じ prompt を別 Provider へ送らず、安全な定型 TALK へ縮退する |
| TTS | timeout | `PROVIDER_TIMEOUT` | 次 TTS Provider、cache、字幕と jingle の順で縮退し、`QueueItem` を再生可能にする |
| TTS | unreachable | `PROVIDER_UNREACHABLE` | 次 TTS Provider または安全な audio fallback へ切り替える |
| TTS | malformed / empty / non-WAV response | `PROVIDER_BAD_RESPONSE` | 次 TTS Provider または安全な audio fallback へ切り替える |
| TTS | safety block / request rejected | `PROVIDER_REJECTED` | 同じ text / voice 指定を別 Provider へ送らず、安全な cache または jingle へ縮退する |
| Music Generation | timeout | `PROVIDER_TIMEOUT` | 即時再試行せず cache、archive、local asset、jingle、TTS の順で縮退する |
| Music Generation | unreachable | `PROVIDER_UNREACHABLE` | 同一 `QueueItem` を再利用して再生可能な fallback へ差し替える |
| Music Generation | malformed / empty / unknown response | `PROVIDER_BAD_RESPONSE` | 未知外部 code を含めて正規化し、再生可能な fallback へ差し替える |
| Music Generation | safety block / request rejected | `PROVIDER_REJECTED` | 同じ prompt / lyrics を別 Provider へ送らず、安全な local asset または jingle へ縮退する |

全ケースで、失敗試行の `provider_job.status=FAILED` と成功した fallback 試行の `SUCCEEDED`、同一 `correlationId`、playout の `DEGRADED` と共通 error code の `degraded_reason` を確認する。
`provider_job.status` へ `DEGRADED` は追加しない。
LLM は Provider 試行ごとに `provider_job` を作る。回復可能な失敗では次 Provider の job を同じ `correlationId` で作成し、外部 Provider で成功しなかった場合は `TemplateScriptProvider` の定型台本を `providerKey=template-script` の別 job として記録する。定型台本への縮退は実 Provider の失敗 job を成功へ書き換えない。
script / TTS cache hit では Provider を呼び出さず、現在の queue item と `correlationId` を持つ論理 job、`externalRef=cache-hit:{sourceAssetId}`、clone asset の現在 job ID を確認する。TTS asset は `scriptAssetId` / `scriptProviderJobId` から成功 script へ遡れ、metadata に生の normalized text、voice hint、参照音声 path、レター本文、秘密値を含まないことを service test で確認する。`LETTER` 由来は script / TTS の通常 cache hit 対象にしない。
`/api/health`, `/api/monitor/summary`, SSE `provider.health.changed` は、既定 Provider が失敗して fallback Provider が利用可能なら `DEGRADED`、Provider chain 全体が利用不能なら `DOWN` を同じ意味で返す。
prompt、lyrics、letter body、radioName、API key、管理トークン、Provider 応答本文は `provider_job`, asset metadata、API、SSE、標準ログへ残さない。
