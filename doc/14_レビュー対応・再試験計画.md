# SeedShiftRadio 実装レビュー対応・再試験計画

## 1. 目的

本書は、実装レビュー指摘を既存設計書に照らして整理し、実装順、設計更新、再試験計画、サブエージェント割当までを一体で定義する。

前提:

- 設計の正本は `doc/` 配下とする
- 現ワークツリーは Spring Boot サーバー実装が中心で、`/web` と `/workers/musicgen` は未作成である
- 現物確認の対象は主に `RadioService`, `LetterService`, `MonitorService`, `ProgrammingService`, `StationAdminService`, `V1__bootstrap.sql`, `RadioApiTests` とする

## 2. 指摘の分類と優先順位

| 優先 | 対象 | 位置づけ |
|---|---|---|
| `P0` | `B-02`, `B-03`, `B-04`, `B-01`, `B-08`, `B-09`, `B-10` | 既存サーバー骨格の整合性と API 契約を先に安定化する |
| `P1` | `A-03`, `A-04`, `A-05`, `B-05`, `B-06`, `B-07`, `A-06` | 設計どおりに拡張するための基盤と共有契約を埋める |
| `P2` | `A-01`, `A-02`, `C-01`, `C-02` | MVP 到達と UI / Provider / 試験導線を完成させる |

判断基準:

- `Server` を radio status, queue, settings, persistence の正本に保つ
- `Web` は表示、操作、SSE 購読、音声再生に集中させる
- 重い AI 推論と MusicGen は `Provider` / `Worker` として分離する
- `Web` と将来の `C# Native Client` が同じ API 契約を使える状態を維持する

## 5. 再試験計画

### 5.1 Docker 不要の service / slice test

対象:

- `TuneRequest.resumePlayback` の分岐
- playback event の session/item 整合性と前状態ガード
- レター状態遷移と `adoptedInSessionId`
- `SpeechDirectiveAssembler`
- ProgramTemplate 保存時の `segmentType` 検証
- `ProviderHealthChecker` の状態分類
- `config-service` の妥当性検証

目的:

- `doc/11` 10.1 に沿って、Docker がない環境でも主要ロジックを再現できるようにする
- `C-01` の再現性不足を先に潰す

### 5.2 API / MockMvc 再試験

対象:

- `POST /api/radio/tune`
- `POST /api/radio/play`
- `POST /api/radio/stop`
- `POST /api/radio/playback-events`
- `GET /api/radio/next-speech-directive`
- `POST /api/letters/{id}/status`
- `GET /api/settings`, `PUT /api/settings`, `POST /api/settings/test-connections`
- `GET /api/monitor/summary`
- `GET /api/assets/audio/{assetId}.wav`

観点:

- 正常系
- 不正状態遷移
- 認可失敗
- `400` / `409` への正規化
- `audio/wav` の MIME
- Provider 状態が `UP / DEGRADED / DOWN` で返ること

### 5.3 Integration / Testcontainers 再試験

対象:

- Flyway migration の適用
- `frequency_mhz` unique 制約
- `generated_asset`, `provider_job`, `play_history`, `client_capabilities` 追加後の整合
- JobRunr を有効化した `WarmupQueueJob`, `QueueRefillJob`, `GenerateMusicJob`
- SSE の `Last-Event-ID` 再送
- Provider mock を使った timeout / unreachable / partial success

観点:

- DB 制約がアプリ外競合でも効くこと
- 非同期ジョブ後も queue 正本と block 正本が崩れないこと
- `MusicGen` 失敗時に `DEGRADED` で継続できること

### 5.4 Web UI / E2E 再試験

最初の happy path 3 本:

1. `Tune -> Play -> queue 更新 -> audio 再生開始`
2. `Letter 投稿 -> 管理一覧反映 -> ADOPTED -> 放送履歴反映`
3. `SSE 切断 -> Last-Event-ID 再接続 -> 再同期`

追加で必要なシナリオ:

- `/settings` で Provider 接続テスト
- `/monitor` で `DEGRADED` 表示
- `CLIENT_TTS` 能力申告時の `SpeechDirective` 確認

### 5.5 手動確認

- Tune から音が出るまでが 5 秒以内
- MusicGen / TTS が `DOWN` でも停止ではなく縮退継続になる
- 再起動後に設定、履歴、client capability メタが期待どおり残る
- 標準ログに `radioName`, letter body, prompt 本文, API key, 管理トークンが露出しない

## 7. 直近の着手メモ

- まず `RadioService` の状態遷移表を `doc/05` に追記してから実装へ入る
- `LetterService` の採用 API は `sessionId` をどう持たせるかを `doc/12` と `doc/02` で先に確定する
- `StationAdminService` の周波数検証は migration と同時に変える
- `ProgrammingService` の `SegmentType.valueOf()` 例外は保存時検証へ寄せる
- `MonitorService` の固定 `UP` は mock provider でも置き換えられる構造にする
- `resumePlayback=true` の契約は「`POST /api/radio/tune` の初回応答は `PREPARING`、warmup 完了後は Server が自動で `PLAYING` へ進めてよい」に統一し、`RadioApiTests` の期待値もこの前提へ揃える
- `./gradlew test` は現環境では `~/.gradle` 配下の lock と権限差分で失敗することがあるため、再試験時は `GRADLE_USER_HOME=/tmp/seedshift-gradle` など書き込み可能な場所を明示して実行する
