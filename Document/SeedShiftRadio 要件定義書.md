## 2. 背景・目的
本システムは、周波数（ダイヤル）操作によって“局（ステーション）”を切り替え、局ごとに異なるAIパーソナリティが雑談・雑学・トレンド等をラジオ番組風に話し、必要に応じて音楽を再生するアプリケーションである。  
また、AI呼び出しAPI（LLM）および音声生成（TTS）を差し替え可能とし、ローカル運用に適した構成を提供する。

追加要件として、ユーザーが“ラジオレター（お便り）”形式で番組への要望や感想を投稿し、放送内で取り上げたり、放送後に返信するなどの双方向性を提供する。

---

## 3. スコープ

### 3.1 対象範囲（スコープ内）
- 離散チャンネル方式の周波数（ダイヤル）操作と局切替
- ステーション（局）ごとのパーソナリティによるトーク生成
- トーク（生成音声）と音楽（主にローカル音源）の連続再生（番組進行）
- LLMプロバイダ（API）差し替え可能な設計・設定
- TTSプロバイダ（音声生成）差し替え可能な設計・設定
- 設定の永続化（基本設定ファイル）とエクスポート/インポート
- 生成物（台本/音声）キャッシュのオプション制御
- ログ／エラー時フォールバック
- ラジオレター（お便り）投稿・管理・放送内反映・返信（やり取り）

### 3.2 対象外（スコープ外）
- 著作権管理が必要な音楽ストリーミング配信（権利処理を伴う配信）
- 外部配信プラットフォームとしての公開配信
- 法務・規約準拠を目的とする高度なモデレーションの完全実装（ただし最低限の安全設計は行う）

## 4. 用語定義
| 用語 | 定義 |
|---|---|
| 周波数（Frequency） | ユーザーが操作するダイヤル値（MHz）。離散チャンネルにマッピングされる表示値。 |
| チャンネル（Channel） | 離散的に定義された周波数点。1チャンネルが1ステーションに対応する。 |
| ステーション（Station） | 周波数（チャンネル）に紐づく“局”。番組編成とパーソナリティ設定を持つ。 |
| パーソナリティ（Personality） | 口調・キャラ・専門性・禁則等を定義した話者プロファイル。 |
| シード（Seed） | チャンネルごとの初期パーソナリティ生成の入力値。再現性確保のため保存する。 |
| セグメント（Segment） | 番組の最小単位（トーク、ジングル、音楽枠、レターコーナー等）。 |
| プロバイダ（Provider） | LLM/TTS等の実装（差し替え対象）。 |
| プレイアウト（Playout） | 再生制御（キュー管理、音量調整、クロスフェード等）。 |
| ラジオレター（Letter） | ユーザーが番組へ送る投稿（要望・感想・質問等）。 |
| レターコーナー | 放送内でレターを読み上げ、回答やコメントを行うセグメント。 |
| キャッシュ（Cache） | 生成台本/生成音声などのローカル保存（オプションで制御）。 |

## 5. システム概要

### 5.1 システムの全体像
- ユーザーは周波数ダイヤル操作でチャンネル（ステーション）を切り替える。
- ステーションは番組編成（セグメント構成）とパーソナリティ設定を持つ。
- トークはLLMで台本生成し、TTSで音声化して再生する。
- 音楽はユーザーが利用権を有するローカル音源を再生する。
- レター機能により、ユーザーは番組へ投稿し、放送内での読み上げや返信（やり取り）を行う。
- LLM/TTSはプロバイダ抽象化により差し替え可能とする。

### 5.2 想定利用シーン
- 作業用BGM兼トーク（ラジオ代替）
- 雑学・トレンドの音声での消費
- ローカルLLM/ローカルTTSの実験基盤
- “お便り”を介した番組カスタマイズ（話題リクエスト、改善要望）

## 7. 前提・確定事項（方針）

### 7.1 周波数マッピング（確定）
- 周波数は **離散チャンネル方式** とする。
  - 例：76.5 / 78.1 / 80.2 …（設定ファイルで定義）
- チャンネルは並び順（周波数昇順）を原則とし、スキャン（次/前）に利用する。

### 7.2 パーソナリティ（確定）
- パーソナリティは **チャンネルごとにシードを保存** する。
- ただし、再現性を担保するため、シードから生成した **PersonalityProfile（生成結果）自体も保存** する。
- 生成ロジック変更に備え、`personalityGenVersion` を保存する（推奨）。

### 7.3 生成単位（方針）
- 実装難易度・体験品質の観点から段階導入する。
- **MVPは短尺セグメント方式（例：20〜60秒相当）＋先読みバッファ** を採用する。
- ストリーミング生成は将来拡張（Phase 3）とする。

### 7.4 キャッシュ（確定）
- ローカル保存キャッシュはオプションで制御可能とする。
- キャッシュ対象は少なくとも以下を想定する：
  - 台本（Script）
  - 音声（Audio）
- TTL、最大容量、削除ポリシー（LRU等）を設定で管理できる。

### 7.5 設定保存（確定）
- 設定値は基本設定ファイル（JSON/YAML）に保存する。
- APIキー等の機密情報は設定ファイル直書きを避け、参照方式（例：環境変数参照）を推奨する。

## 9. 詳細機能要件

### 9.1 周波数・ステーション

#### 9.1.1 周波数操作（FR-001）
- 入力：ダイヤル（スライダー/ノブ/数値）
- 出力：現在周波数（MHz）、対応ステーション名の表示
- 周波数は離散値であり、ユーザー操作により定義済みチャンネルへスナップする。

#### 9.1.2 局切替（FR-002）
- 周波数変更時、対応ステーションへ切替える。
- 切替時の最低要件：
  - 現在の再生を停止またはフェードアウト（実装方針に従う）
  - 切替先局のプレイアウトキューを初期化
  - 切替先局のオープニングまたは次セグメントから再生開始

#### 9.1.3 ステーション定義（FR-003）
ステーションは以下の情報を保持する：
- 基本情報：ID、名称、説明、ジャンル
- チャンネル情報：周波数（MHz）
- パーソナリティ：
  - seed（必須）
  - personalityProfile（生成結果、必須）
  - personalityGenVersion（推奨）
- 番組編成：セグメント構成（順序/比率/尺）
- 音声/音楽ルール：BGM/音源フォルダ/ジングル等
- レター方針（任意）：取り上げルール、読み上げテンプレ等

---

### 9.2 番組編成（セグメント）

#### 9.2.1 セグメント種別
- トーク（雑談、雑学、トレンド等）
- 音楽枠（ローカル音源再生）
- ジングル/SE（局演出）
- レターコーナー（お便り読み上げ＋回答）
- 告知/CM風（任意）

#### 9.2.2 生成単位（方針の具現化）
- MVPでは短尺セグメント方式を採用する：
  - 目標尺：20〜60秒相当（設定値で変更可能）
  - 先読み：次のNセグメントを常に準備（設定値で変更可能）
- 将来拡張として長尺セグメント、ストリーミング生成を検討可能とする。

---

### 9.3 トーク生成・音声生成

#### 9.3.1 台本生成（FR-004）
- セグメント単位で台本（読み上げ文）を生成する。
- 反映すべき要素：
  - ステーション/パーソナリティ設定（口調、テンポ、専門性、禁則）
  - セグメント種別（雑談/雑学/トレンド/レター回答等）
  - 目標尺（秒 or 文字数）
- 出力は読み上げに適した文体とし、不要なメタ情報（指示文等）を含めない。

#### 9.3.2 音声生成（FR-005）
- 台本をTTSプロバイダに渡し、音声ファイル（またはストリーム）を生成する。
- パーソナリティに紐づく音声プロファイル（話者/速度/ピッチ等）を適用できる。

---

### 9.4 再生（プレイアウト）

#### 9.4.1 連続再生（FR-006）
- 番組編成に従い、再生キューを生成して順次再生する。
- キュー項目種別：
  - トーク（生成音声）
  - 音楽（ローカル音源）
  - ジングル/SE
  - レターコーナー（生成音声）
- 再生が途切れないよう、先読み生成（バッファ）を行える設計とする。

#### 9.4.2 音楽再生（FR-007）
- ローカル音源フォルダから音源を読み取り再生できる。
- 選曲方式（最低限）：
  - ランダム
- 推奨：
  - 直近再生の重複回避
  - 音量正規化、クロスフェード、ダッキング（FR-016）

> 注意：権利処理を伴う配信は対象外。音源はユーザーが利用権を有するローカルファイル等を前提とする。

---

### 9.5 ラジオレター（お便り）機能

#### 9.5.1 レター投稿（FR-020）
- ユーザーはアプリ内でレターを作成し、対象ステーション（または共通）へ送信できる。
- 入力項目（最低限）：
  - 宛先ステーション（Station ID）または「共通」
  - 件名（任意）
  - 本文（必須）
  - ラジオネーム（任意：FR-024）
- 投稿時、状態を「未読」として保存する。

#### 9.5.2 レター管理（FR-021）
- レター一覧表示（フィルタ推奨）：
  - ステーション別
  - 状態別（未読/保留/採用/返信済 等）
- 状態遷移（最低要件）：
  - 未読 → 保留
  - 未読/保留 → 採用（放送で取り上げ対象）
  - 採用 → 返信済（放送またはテキスト返信後）
- 採用/不採用などの運用はローカル前提でユーザー操作可能とする。

#### 9.5.3 放送内で取り上げ（FR-022）
- 番組編成に「レターコーナー」を組み込める。
- レターコーナーの動作：
  1) レターを読み上げ（必要に応じ要約）
  2) パーソナリティが回答/コメント
  3) 次のレター/次セグメントへ繋ぐ
- 取り上げ対象選定ルール（最低要件）：
  - 採用ステータスのレターを優先して取り上げる。
- 放送で取り上げたレターは「放送済」フラグ（またはpickedAt）を付与する。

#### 9.5.4 返信/やり取り（FR-023）
- レターに対する返信をスレッドとして保持できる（SHOULD）。
- 返信形式：
  - テキスト返信（アプリ内表示）
  - 放送内返信（レターコーナーで読み上げ回答）
- 返信は当該ステーションのパーソナリティ設定を反映した文体で生成する。

#### 9.5.5 安全設計（レター）
- レター内容はLLMに渡るため、最低限以下を考慮する：
  - 入力は引用扱いとし、システム命令・設定変更指示として解釈しない（プロンプト注入対策）
  - 機密情報（APIキー等）を出力・ログ出力しない
  - 個人情報の過度な生成を抑制する（既定方針）

## 10. プロバイダ差し替え要件（LLM/TTS）

### 10.1 LLM差し替え（FR-008）
- LLM呼び出しをプロバイダインターフェースで抽象化する。
- 設定可能項目（例）：
  - providerType（openai互換/ローカル/他社等）
  - baseUrl
  - apiKeyRef（参照方式：例 env）
  - model
  - 生成パラメータ（temperature等）
  - timeout / retry / rate limit（可能な範囲で）
- Providerごとの差異（ストリーミング、構造化出力など）は機能フラグまたは適応層で吸収する。

### 10.2 TTS差し替え（FR-009）
- TTSも同様に抽象化する。
- 設定可能項目（例）：
  - providerType（ローカル/クラウド等）
  - baseUrl
  - apiKeyRef
  - voiceId / style / speed / pitch

---

## 11. 設定・データ要件

### 11.1 設定永続化（FR-010）
- 設定は基本設定ファイル（JSON/YAML）に保存する。
- 設定ファイルはスキーマバージョン（`configVersion`）を持つことを推奨する。
- エクスポート/インポートを提供する（SHOULD）。

### 11.2 機密情報の扱い
- APIキー等は設定ファイルに直書きせず、`apiKeyRef` で参照する方式（例：`env:OPENAI_API_KEY`）を推奨する。
- ログや画面表示で機密情報を露出しない。

### 11.3 キャッシュ（FR-017）
- キャッシュはオプションで有効/無効を切り替え可能とする。
- 設定項目（例）：
  - `cache.enabled`
  - `cache.dir`
  - `cache.ttlDays`
  - `cache.maxSizeMB`
  - `cache.evictPolicy`（例：LRU）
  - `cache.script.enabled`
  - `cache.audio.enabled`

### 11.4 データモデル（案）
- Station
  - id, name, description, genre
  - frequencyMHz（離散）
  - seed, personalityProfile, personalityGenVersion
  - scheduleTemplateId, musicRules, letterPolicy
- PersonalityProfile
  - displayName, stylePrompt, topicBias, ngPolicy, voiceProfile
- ScheduleTemplate
  - segments[]（順序、比率、尺）
- SegmentDefinition
  - type, targetDuration, promptTemplateId, requiredData
- ProviderConfig（LLM/TTS）
- PlayoutQueueItem
  - kind（talk/music/jingle/letter）, source, duration, metadata
- GeneratedAsset
  - scriptText, audioPath, hash, createdAt, providerInfo
- Letter
  - id, stationId(nullable), subject(optional), body
  - radioName(optional), status, pickedAt(optional)
  - createdAt, updatedAt
- LetterThreadMessage
  - id, letterId, authorType(USER/AI), message, createdAt

## 12. 非機能要件

### 12.1 可用性（FR-011）
- LLM/TTSが失敗してもアプリ全体が停止しないこと。
- 生成失敗時の基本動作：
  - リトライ（上限回数設定）
  - 代替セグメントへ移行（スキップ）
  - キャッシュ済み資産の再利用
  - 無音回避（ジングル/短い案内など）

### 12.2 性能・遅延
- MVPは短尺セグメント方式により途切れにくい体験を優先する。
- 先読みバッファ数を設定可能とする。

### 12.3 セキュリティ
- 設定ファイルの機密情報露出を避ける（参照方式推奨）。
- ログに機密情報を出力しない。

### 12.4 監査性・運用性
- 生成ログ（どの局で何を生成したか、エラー等）を記録可能とする（SHOULD）。
- キャッシュクリア、ログローテーション等の運用機能を提供する（SHOULD）。

### 14.1 LLM Provider I/F（概念）
- generateScript(context) -> scriptText
- 任意：streaming対応、JSON構造化出力対応

### 14.2 TTS Provider I/F（概念）
- synthesize(scriptText, voiceProfile) -> audioAsset
- 任意：ストリーミングTTS対応

## 15. エラー・例外要件

### 15.1 LLM失敗
- リトライ → スキップ → キャッシュ再生 → 代替セグメント（短い案内等）

### 15.2 TTS失敗
- リトライ → 代替voice（可能なら） → テキスト表示のみ → セグメントスキップ

### 15.3 音源なし
- 音楽枠をトークへ置換、または無音回避ジングル/SEを再生

### 15.4 レター処理失敗
- 読み上げ生成失敗：別レターへ切替／要約なし短縮／レターコーナースキップ
- 返信生成失敗：保留状態にし、後で再生成可能とする

## 16. 制約・留意事項
- 音楽再生はユーザーが利用権を有するローカル音源等に限定する。
- “トレンド/ニュース”の取得を行う場合、情報ソース（RSS、Web等）と更新頻度、出典表示方針を別途定義する（将来拡張）。

## 17. MVP定義

### 17.1 MVP範囲
- 離散チャンネルによる局切替
- 1〜3局程度
- 固定編成（トーク→音楽→トーク、必要に応じレターコーナー）
- LLM 1実装（OpenAI互換等）＋差し替えI/F
- TTS 1実装＋差し替えI/F
- ローカル音源再生
- 短尺セグメント生成（20〜60秒相当）＋先読みバッファ（例：2）
- レター投稿、レター管理（最小）、レターコーナーでの読み上げ・回答

### 17.2 次フェーズ（例）
- 返信スレッドの本格運用（FR-023の強化）
- ジングル/SE、ダッキング/クロスフェード
- 掛け合い、時間帯編成
- 外部データ注入（天気/RSS等）

- レターのモデレーション方針（NGワード、カテゴリ制限など）の粒度
- レター読み上げ方針（全文/要約/抜粋）の既定値
