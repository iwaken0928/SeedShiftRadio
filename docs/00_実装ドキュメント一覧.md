# AIローカルラジオアプリ 実装ドキュメント一覧

## 1. 目的

本書は [aiローカルラジオアプリ_基本設計書](./aiローカルラジオアプリ_基本設計書.md) を実装へ落とし込むための入口ドキュメントである。MVPで先に固めるべき設計書、採用するOSS、実装順序、未確定事項をまとめる。

## 2. 前提

- 要件の基準文書は 2026-03-06 版の再定義書とする
- 初期構成は `Java Server + Web UI + Local AI Service` とする
- 将来の `C# Native Client` を阻害しない API First を維持する
- 生成系は JVM に閉じ込めず、HTTP または別プロセス連携を前提とする

## 3. MVPの標準採用スタック

| 領域 | 採用方針 | 主なOSS |
|---|---|---|
| サーバー基盤 | Java 21 ベースの API / Playout / 設定 / 監視の中核 | Spring Boot, Spring MVC, Spring Actuator, springdoc-openapi |
| リアルタイム通知 | まずは一方向通知を優先し、双方向は必要時に限定 | SSE, Spring WebSocket |
| Web UI | 動的なラジオUIと字幕・キュー表示を優先 | Next.js, React, TypeScript, TanStack Query, Zustand, Tailwind CSS |
| DB | 設定以外の運用データの正本 | PostgreSQL, Flyway |
| ベクトル拡張 | 将来のレター要約・再利用文脈向け拡張枠 | pgvector |
| ジョブ制御 | 先読み生成、音楽生成、再試行を管理 | JobRunr |
| LLM | `ScriptProvider` で抽象化し、JDK HTTP adapter からローカル推論サービスを接続 | Ollama, OpenAI 互換 API。Spring AI は将来の adapter 候補 |
| TTS | MVPの安定読み上げ候補。高品質候補は OpenAI互換 server 経由で追加する | VOICEVOX, Irodori-TTS-Server |
| TTS代替 | キャラクター性や将来差し替え候補 | AivisSpeech, Style-Bert-VITS2 |
| MusicGen | 重い推論を分離したローカルワーカー | FastAPI ベース Python Worker, ACE-Step 系 |
| 音声再生 | Webの逐次セグメント再生を優先 | HTMLAudioElement, howler.js |
| テスト | API/UI/DB/Worker を現実に近い形で検証 | JUnit 5, Testcontainers, Vitest, Playwright |
| 将来のネイティブUI | Windows向け音声エンジン統合の拡張先 | WPF, CommunityToolkit.Mvvm, NAudio |

## 6. 現時点の設計判断

- SSR vs SPA は二者択一にせず、`Next.js App Router` のハイブリッド構成を採用する
- リアルタイム通知は MVP では `SSE` を標準とし、双方向制御が必要になった時点で WebSocket を追加する
- DB は `PostgreSQL` を標準とし、`SQLite` は開発簡易プロファイルに限定する
- MusicGen は Java 直結ではなく `Python Worker + HTTP` を標準とする
- 日本語TTSは `VOICEVOX` を安定 fallback とし、ラジオパーソナリティ品質を上げる server-side TTS 候補として `Irodori-TTS-Server` を取り込む
- 将来の Client-side TTS を見据え、`SpeechDirective` を API 契約に含める
- 管理系 API は `X-Admin-Token` を必須とし、一般操作 API と分離する
- `pgvector` は MVP へ含めず、関連レター検索が必要になった段階で追加する
- C# Native Client も REST + SSE を標準とし、不足が確認された場合だけ WebSocket を追加する
