# AIローカルラジオアプリ 運用・監視・セキュリティ・テスト設計書

## 1. 目的

本書は非機能要件、監視、運用、セキュリティ、プライバシー、試験方針を一つにまとめた実装補助文書である。

## 2. 非機能目標

| 項目 | 目標 |
|---|---|
| Tune から再生開始 | 5 秒以内 |
| 通常時 Ready 件数 | 2 件以上 |
| MusicGen 失敗時 | 再生停止しない |
| 再起動後の設定/履歴保持 | 維持されること |
| 同時接続 | 3 から 5 クライアント程度 |
| ローカル復旧目標 RTO | 15 分以内 |

## 3. 監視

### 3.1 推奨OSS

- Spring Actuator
- Micrometer
- Prometheus
- Grafana
- logstash-logback-encoder

### 3.2 主要メトリクス

- queue ready count
- queue ready duration
- provider response time
- provider error count
- music job running count
- cache hit rate
- disk free space

## 4. ログと監査

- 構造化 JSON ログを標準とする
- `correlationId`, `stationId`, `sessionId`, `queueItemId` を出す
- 設定変更、局切替、レター状態変更、縮退遷移を監査対象にする
- レター本文全文、プロンプト全文、秘密値は標準ログへ出さない

## 5. Runbook 最低項目

- Provider 停止時の切り分け
- Queue が詰まった時の再生成手順
- ディスク不足時の古いキャッシュ削除手順
- MusicGen Worker 停止時の縮退運転
- PostgreSQL 障害時の復旧確認

## 6. バックアップ

対象:

- `config.json`
- PostgreSQL dump
- 読み辞書
- 生成資産メタデータ
- 手動編集した局設定

生成音声・生成音楽の実ファイルは再生成可能なものを除き、毎日フルバックアップ対象にしない。

## 7. セキュリティ

- bind host は既定で `127.0.0.1`
- 管理系 API は `X-Admin-Token` を要求する
- CORS は same-origin を基本とする
- レター入力は prompt injection 前提で扱う
- ファイルパスは許可済みルート以外を参照させない
- CLI 連携は Java 本体から直接実行せず worker 経由とする

## 8. プライバシー

- `radioName`, letter body, 放送履歴は個人データ相当として扱う
- 画面・ログ・監視へそのまま露出しない
- 保持期間と削除方針を明文化する
- プロンプトへ個人情報を混ぜる場合は必要最小限に限定する

## 9. OSS/モデル/音源ライセンス管理

最低でも以下を台帳管理する。

- OSS 名称
- バージョン
- ライセンス
- 再配布義務
- モデル利用条件
- 生成物の利用条件

特に TTS モデル、音声モデル、音楽生成モデルは本体 OSS と別条件のことがあるため分けて管理する。

## 10. テスト戦略

### 10.1 サーバー

- `JUnit 5`
- `Testcontainers`
- Provider mock を使った service test
- Queue / Fallback の状態遷移 test

### 10.2 Web UI

- `Vitest`
- `Playwright`
- Tune, Play, Letter 投稿, SSE 再接続の E2E

### 10.3 Worker

- FastAPI contract test
- 長時間ジョブの timeout test
- 失敗時 metadata の整合 test

### 10.4 品質確認

- 日本語正規化の golden test
- 読み辞書の回帰 test
- フォールバック時に無音にならないことのシナリオ test

## 11. 実装前に必ず確認する項目

- MusicGen モデルの利用条件
- Native 向け音声エンジンのライセンス
- ローカル音源の利用条件
- 公開ポートの有無
- 管理トークンの保存方法
