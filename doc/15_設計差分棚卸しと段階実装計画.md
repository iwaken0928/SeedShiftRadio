## 4. 今回確認した設計上の問題

### 4.1 production の Web 管理認証を成立させた

Server の管理 API が `X-Admin-Token` を必須とする共有契約は維持した。

`P0-11` で Web 管理用の login / session / logout、署名済み `HttpOnly` Cookie、session 固有 CSRF token、同一 origin `/api-proxy` を実装した。BFF は browser 由来の credential header と Cookie を upstream へ転送せず、認証済み ADMIN request だけに server-side の `SEEDSHIFT_ADMIN_TOKEN` を注入する。

`NEXT_PUBLIC_SEEDSHIFT_ADMIN_TOKEN`、`NEXT_PUBLIC_ADMIN_TOKEN`、直接 Server URL を指定する browser API base は削除した。production compose と deploy env は `SEEDSHIFT_WEB_ADMIN_PASSWORD`、`SEEDSHIFT_WEB_SESSION_SECRET`、`SEEDSHIFT_ADMIN_TOKEN` を Web runtime だけへ渡し、管理 session smoke で未認証拒否、CSRF、認証済み proxy、logout を確認する。

### 4.2 TTS の最終縮退が voice hint により外部 adapter へ戻る

`seedshift-placeholder` provider の adapter 推定より `SpeechDirective.voiceHint` が優先されていた。

このため VOICEVOX 失敗後の placeholder fallback でも VOICEVOX HTTP 接続を再実行し、queue warmup が完了しなかった。

`P0-10` で provider key の最終縮退を優先するよう修正し、回帰 test を追加した。

### 4.3 外部 Provider 仕様の更新が設計書へ反映されていない

Irodori-TTS-Server は `stream_format=sse` による chunk-level SSE を提供している。

現行 SeedShiftRadio adapter は完成 WAV を保存するため、upstream capability と adapter の有効状態を分けて記述する。

実際に playout 契約へ採用するかは `P0-02b` で決定する。

### 4.4 API 契約の drift 検出を追加した

Controller、生成 OpenAPI、`doc/02` に分散していた endpoint、DTO、認証区分を `P1-18` で比較対象へ統合した。

`ApiContractTests` は `/api/openapi` の SHA-256 snapshot、Spring MVC handler の `X-Admin-Token` header、`api-auth-matrix.json`、`doc/02` の認証表を照合する。

GitLab CI の `api-contract` job で `./gradlew apiContractTest` を独立実行する。手書き Web client と将来の C# client fixture の比較は `P2-12` で追加する。

### 4.5 運用上必要な永続化と復旧が不足する

監査 summary は process memory 上の SSE 履歴に依存する。

`config.json` は schema migration と raw backup / restore を持たない。

読み辞書は hard-coded 共通語だけで、global / station / persona 層を運用できない。

停止した process の `provider_job=RUNNING` を回収する経路がない。

これらを `P1-19` から `P1-22` に分割する。

### 4.6 設計・リポジトリ衛生が現状とずれている

旧 `doc/14` と `doc/15` は実装済み作業を未実装とし、現在の GitLab-first 運用と矛盾する固定サブエージェント割当を残していた。

また、生成物が Git 管理され、ローカル起動ガイドが ignore されていた。

設計書は今回更新し、生成物整理とガイド正本化を `P2-11` で追跡する。

### 4.7 Web 依存に既知脆弱性が残っている

Next.js `15.5.14`、Vitest、Vite、PostCSS、`ws` に production または development の既知 advisory が残っていた。

`P0-12` で同一 major / minor 内の修正版と最小 override へ更新し、`npm audit` を 0 件にした。

### 4.8 Provider error / fallback 契約を共通化した

`P0-05` で LLM、TTS、Music Generation の失敗を共通 Provider error code へ揃えた。

Provider chain の fallback は `PROVIDER_UNREACHABLE`, `PROVIDER_TIMEOUT`, `PROVIDER_BAD_RESPONSE`, `PROVIDER_RESOURCE_EXHAUSTED` と、TTS 固有の `VOICE_REF_NOT_FOUND`, `VOICE_CONSENT_REQUIRED` だけで許可する。
安全性ポリシーによる拒否を含む `PROVIDER_REJECTED`、認証失敗の `PROVIDER_AUTH_FAILED`、中断の `PROVIDER_INTERRUPTED` では同じ要求を別 Provider へ自動送信しない。

論理生成ジョブの `provider_job.status` は `FAILED` または `SUCCEEDED` とし、`DEGRADED` は Provider health と playout state で表す。
TTS は Provider 試行を個別 job として追跡し、Music Generation の Provider chain は最終 Provider と論理ジョブの最終結果を一つの job に残す。
外部 Provider または Worker の未知 error code は `PROVIDER_BAD_RESPONSE` へ正規化する。

## 7. 段階実装計画

### 7.1 Gate 0: 既存再生経路を安定化する

1. `P0-10` の `server-docker` を再実行する。
2. Tune、queue warmup、playback event、play history、monitor summary が回復したことを確認する。
3. 検証結果を GitLab `#23` へ記録する。

この Gate が失敗している間は、fallback に関係する大きな provider 変更を統合しない。

### 7.2 Gate 1: production 管理面と契約 drift を止める

1. `P0-11` で Web 管理 session と CSRF 境界を実装した。production pipeline と HTTPS 利用者経路で smoke を継続する。
2. `P0-12` で Web dependency advisory を解消し、`npm audit` を release gate にする。
3. `P1-18` で OpenAPI と認証マトリクスの CI gate を追加する。
4. `/letters`、`/settings`、`/monitor` の未認証拒否と認証済み操作を production 相当 E2E で確認する。

`P0-11` と `P1-18` は実装・focused test 済みであり、既存 Server API 契約と Web BFF 専用認証 endpoint の境界を維持する。

### 7.3 Gate 2: 実 LLM / TTS 放送品質を完成する

`P0-05` の共通 error / fallback 契約は固定済みである。

`P0-02c` の VoiceProfile metadata と `P0-05a` の日本語品質 guard は実装・検証済みで確認待ちである。

残りの推奨順は `P0-01`、`P0-02b`、`P0-03`、`P0-04` とする。

後続 adapter は `P0-05` の共通分類を使い、adapter ごとの例外分類を増殖させない。

VoiceProfile と同意 metadata の永続化・局 scope は固定済みである。`P0-02b` で TTS runtime 反映を完成してから管理 UI `P1-17` を実装する。

### 7.4 Gate 3: 実音楽生成と運用接続を完成する

1. `P0-06` で実モデル backend と resource limit を実装する。
2. `P0-09` で compose、settings、health、deploy、runbook を同じ provider profile に接続する。
3. GPU smoke、worker down、timeout、fallback asset、再起動後 job 状態を確認する。

### 7.5 Gate 4: 運用耐久性を上げる

`P1-19`、`P1-20`、`P1-21`、`P1-22` は独立して着手できる。

`P1-22` が前提としていた `P0-05` の共通 error / retry 分類は固定済みであり、依存は解除した。

再起動、部分書き込み、古い schema、stale job、秘密値 redaction を failure injection test に含める。

### 7.6 Gate 5: 保守性と将来 Client 契約を固定する

1. `P2-06` で Spring Boot `4.1.0` 追随判断を行う。
2. `P2-11` で生成物とローカル起動ガイドを整理する。
3. `P1-18` 完了後に `P2-12` の C# contract harness を追加する。
