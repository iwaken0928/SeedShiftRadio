# AIローカルラジオアプリ 要件見直し・再定義書（クライアントサーバー版ドラフト）

- 版: 0.1
- 作成日: 2026-03-06
- 対象: ローカル環境で動作するAIラジオアプリ（クライアントサーバー構成）
- 位置づけ: 既存のデスクトップ前提設計を見直し、Javaサーバー + Web UI + ローカルAI連携へ再定義するための上位ドキュメント

---

## 1. 改定の背景

従来案は、Windowsローカルアプリ（WPF / 将来WinUI 3）として、周波数ダイヤル操作、短尺セグメントの先読み再生、LLM/TTS差し替え、ラジオレター機能を中心に設計していた。

本改定では、以下の理由により、クライアントサーバー型へ方針転換する。

- UIをネイティブデスクトップに限定せず、まずはブラウザから利用できるようにしたい
- 将来的に **C# ネイティブクライアント** を追加し、クライアント側ローカル音声エンジン（VOICEROID系を含む）でパーソナリティのトークを再生できるようにしたい
- サーバー側で番組生成・再生制御・永続化・ログ収集を集約したい
- LLM/TTSに加え、ローカルAIによる音楽生成を番組編成へ統合したい
- 将来的にクライアント増加や別UIの追加があっても、API中心で拡張しやすくしたい

本書は、この変更を踏まえて要件を再定義する。

---

## 2. 目標システム像

本システムは、**Java製サーバーアプリケーション**を中核とし、同一サーバーから **Web API** と **Web画面** を提供するローカルAIラジオシステムである。

また、将来拡張として **C# ネイティブクライアント** を追加し、Windowsクライアント上でローカル音声エンジン（VOICEROID系など）を利用した再生にも対応できる構成を前提とする。

ユーザーはブラウザ上のラジオ画面から周波数ダイヤルや局一覧を操作し、局ごとのAIパーソナリティによるトーク、TTS音声、ローカル音源、ローカルAI生成音楽を含む“ラジオ風番組”を視聴できる。

サーバーは以下を担当する。

- 周波数とステーションの解決
- 番組編成と先読みバッファ管理
- LLMによる台本生成
- TTSによる音声生成
- 音楽生成AIへの依頼・取得・キャッシュ
- レター投稿/管理/採用/返信
- 音声アセット配信
- 設定、永続化、ログ、監視

クライアントは以下を担当する。

- Web UI表示、または将来のC#ネイティブUI表示
- ユーザー操作受付
- 現在再生中情報の表示
- 字幕、キュー、レター、設定画面の表示
- 音声の再生制御（ブラウザプレイヤーまたはネイティブ音声エンジン）
- 必要に応じてクライアント側TTS/音声エンジン連携

## 3. スコープ

### 3.1 スコープ内

- クライアントサーバー構成への移行
- JavaサーバーによるWeb API提供
- Javaサーバーから配信されるWeb UI
- 将来のC#ネイティブクライアント追加を考慮したAPI/イベント/データ契約設計
- 離散チャンネル方式の周波数操作と局切替
- 短尺セグメント + 先読みバッファによる連続再生
- LLMによるトーク台本生成
- TTSによる読み上げ音声生成
- ローカル音源の再生
- ローカルAIによる音楽生成の番組組み込み
- ラジオレター（投稿/管理/採用/返信/放送内反映）
- 設定永続化、キャッシュ、ログ、障害時フォールバック
- サーバー状態の監視・簡易ヘルスチェック

### 3.2 スコープ外

- 不特定多数向けの公開配信プラットフォーム化
- 著作権処理を伴う商用音楽配信サービス連携
- 大規模マルチテナント運用
- 高度なユーザー認証・課金・外部決済
- 法務/規約準拠を目的とする完全な著作権判定・モデレーション

## 4. 前提・設計方針

### 4.1 アーキテクチャ方針

- 構成は **Client / Server / Local AI Service** の3層を基本とする
- サーバーは **Java 21 + Spring Boot系** を第一候補とする
- Web UIは同一サーバーから配信する
- APIは **API First** で設計し、画面と外部クライアントの両方から利用できるようにする
- リアルタイム状態反映は **SSE または WebSocket** を用いる
- クライアントは **Webクライアント** と **将来のC#ネイティブクライアント** の複数系統を許容する

### 4.2 再生方式方針

- MVPは **短尺セグメント方式（20〜60秒程度）** を維持する
- サーバーは次セグメントを先読み生成し、クライアントはセグメント単位で順次再生する
- 将来は連結ストリームやHLS等への拡張余地を残す

### 4.3 周波数・ステーション方針

- 周波数は **離散チャンネル方式** を維持する
- 1チャンネル = 1ステーションとする
- ステーションごとに seed / personalityProfile / 編成ルール / 音楽ルール / レター方針を保持する

### 4.4 プロバイダ抽象化方針

- LLM / TTS / Music Generation をすべて差し替え可能なProviderとして抽象化する
- 特に音声出力は **Server-side TTS** と **Client-side TTS** の両方式を許容する
- サーバーの主言語はJavaとするが、ローカルAI実行系は別言語/別プロセスでもよい
- 音楽生成AIは、Javaサーバーから **ローカル推論サービス** として呼び出す

### 4.5 音楽生成AI方針

- ローカルAI音楽生成はMVPスコープに含める
- 実装候補は **ACE-Step系** を第一候補とする
- Javaサーバーへ直接組み込むのではなく、**Python系ローカルサービスまたはジョブ実行プロセス** として分離する
- 将来のC#クライアント側音声再生とは独立に扱い、MusicGen連携とTTS連携を疎結合に保つ
- 生成失敗時は既存ローカル音源、ジングル、トーク置換等へフォールバックし、再生を止めない

### 4.6 設定・保存方針

- 共有設定はサーバー側 `config.json` に保持する
- ブラウザUI状態は LocalStorage 等の軽量クライアント保存を許容する
- 運用データ（レター、履歴、生成メタデータ等）はサーバー側DBへ保存する
- ログはサーバー側ファイルへ出力し、必要に応じて画面から参照できるようにする

### 4.7 フレームワーク選定方針

本システムは、**Javaサーバーを中核**としつつ、**ブラウザでの音声再生・リアルタイム状態反映・動的UI** を重視する。そのため、フレームワークは「Javaだけで完結しやすいか」ではなく、**音声プレイヤー中心のWeb UI** と **API / リアルタイム通知 / AI連携** のバランスで選定する。

#### 4.7.1 候補整理

1. **Spring Boot + Next.js（推奨）**
   - Server: Spring Boot
   - API: REST + SSE / WebSocket
   - UI: Next.js + React + TypeScript
   - 特徴: API中心で疎結合。ラジオ画面のような動的UI、音声プレイヤー、字幕、NowPlaying、キュー表示と相性がよい

2. **Spring Boot + Vaadin Flow / Hilla**
   - Server: Spring Boot
   - UI: Java中心またはReact統合
   - 特徴: Java比率を高く保てる。管理画面や業務UIには強いが、音声プレイヤー主体の細かなWeb体験は個別調整が増えやすい

3. **Quarkus + Next.js**
   - Server: Quarkus
   - API: REST + WebSocket
   - UI: Next.js + React + TypeScript
   - 特徴: 軽量・高速起動に強み。将来コンテナ最適化やネイティブ実行を強く狙うなら有力

#### 4.7.2 推奨構成

本プロジェクトの現時点の推奨は **Spring Boot + Next.js** とする。

理由は以下の通り。

- 既存資料でも **Provider抽象化、UseCase/Coordinator、Web API化しやすい責務分割** が重視されており、Spring Bootへ移行しやすい
- ラジオ画面は **プレイヤー・字幕・バッファ・局切替・リアルタイム反映** が中心で、React系UIの方が実装自由度が高い
- Java側は API / Playout / Job / Persistence / Provider連携 に集中できる
- 将来、Web UIを差し替えてもServer設計を流用しやすい

#### 4.7.3 推奨採用案（具体）

- **Server Framework**: Spring Boot 3.5系を第一候補
- **Web API**: Spring MVC（REST）
- **Realtime**: まず SSE、必要箇所のみ WebSocket
- **AI連携**: Spring AI は LLM抽象化で活用し、TTS / MusicGen は独自Provider I/Fで統合
- **Web UI**: Next.js + React + TypeScript
- **認証**: 必要時に Spring Security を追加

#### 4.7.4 各採用理由

##### Server: Spring Boot 3.5系
- Java製の stand-alone / production-grade アプリを作りやすく、組み込みWebサーバー、外部設定、ヘルスチェック、メトリクス等が揃う
- Spring MVC / WebSocket / Security / Data など関連資産が厚い
- 4.0系も利用可能だが、初回構築では追従コストを抑えるため、まずは3.5系を基準にする

##### AI連携: Spring AI + 独自Provider
- LLM接続は Spring AI の portable API を活かせる
- ただし本システムの中核は **日本語TTS** と **音楽生成AI** を含む複合Provider構成なので、既存資料のProvider抽象化を維持し、TTS / MusicGen は独自I/Fを主軸とする
- つまり、**LLMはSpring AI寄り、TTS/MusicGenはアプリ独自抽象** のハイブリッド構成が適する

##### Web UI: Next.js
- App Router、Server/Client Components、Streaming などがあり、初期表示と動的画面の両立がしやすい
- TypeScript前提で状態管理・音声プレイヤーUI・字幕UI・局一覧UIを整理しやすい
- 将来モバイル向け画面やPWA対応へも展開しやすい

##### 代替案: Vaadin
- JavaだけでUIを書きたい場合は魅力が大きい
- 管理画面、設定画面、一覧系画面には相性がよい
- ただし今回の主役は **ラジオ風プレイヤー体験** であり、音声再生や細かなクライアント制御を考えると、UI専用にReact系を切る方が自然

#### 4.7.5 実装開始時の標準スタック案

- Java 21
- Spring Boot 3.5.x
- Spring MVC
- Spring WebSocket（必要時）
- Spring Actuator
- Spring AI（LLM限定の活用を第一候補）
- Next.js
- React
- TypeScript
- Tailwind CSS
- DBは別紙で決定（SQLite継続またはPostgreSQL）

## 6. 論理構成

### 6.1 全体構成

1. **Client Applications**
   - **Web Client**
     - ブラウザ画面
     - ラジオ画面、レター画面、設定画面、管理画面
     - API呼び出し
     - SSE/WebSocket購読
     - ブラウザ上の音声再生
   - **Future C# Native Client**
     - Windowsネイティブ画面（WPF / WinUI 3 などを候補）
     - API呼び出し
     - SSE/WebSocket購読
     - クライアント側ローカル音声エンジン連携
     - VOICEROID系等のWindows向け音声再生連携を想定

2. **Java Server**
   - REST API / SSE or WebSocket
   - Web UI配信
   - 認可制御（必要最小限）
   - 番組制御（Playout Coordinator）
   - ステーション管理
   - レター管理
   - キャッシュ管理
   - ログ/監視

3. **Local AI Services**
   - LLM Provider
   - TTS Provider
   - Music Generation Provider（ACE-Step系など）
   - 必要に応じて別プロセスまたは別ポートで実行

4. **Persistence / Storage**
   - 設定ファイル
   - DB
   - 生成音声・生成音楽・キャッシュファイル
   - ログ

### 6.2 主要責務分担

- Serverが「番組の正」を持つ
- Clientは「表示と操作」を担う
- AIサービスは「生成専用」に寄せる
- 音声出力は **生成済み音声配信** と **クライアント側音声合成** の二方式を許容する
- 生成済み成果物はServer管理下のキャッシュへ保存し再利用する
- Client固有機能（ネイティブ音声エンジン等）はCapabilityとしてServerへ通知できるようにする

## 8. 詳細要件

### 8.1 クライアント / API

#### 8.1.1 UI提供
- サーバーはWeb画面を配信する
- 将来のネイティブクライアント追加を妨げないよう、UI固有ロジックはAPI背後へ寄せる
- 画面は少なくとも以下を持つ
  - ラジオ画面
  - レター画面
  - 設定画面
  - 任意で管理/監視画面

#### 8.1.2 API方式
- 基本はREST APIとする
- リアルタイム情報は SSE または WebSocket を用いる
- APIは将来の別クライアントからも使える粒度で設計する
- 再生要求に対して、Serverはクライアント能力に応じて以下のどちらかを返せるようにする
  - 生成済み音声アセット
  - 読み上げ用スクリプト + 発話メタデータ

#### 8.1.3 クライアント保存
- 画面レイアウトや最後に開いたタブ等の軽量状態はクライアント側保存を許容する
- サーバー設定とクライアント設定を分離する
- ネイティブクライアント固有の音声エンジン設定はクライアント側保存を基本とする

### 8.2 ステーション / 周波数

#### 8.2.1 周波数操作
- 周波数は離散値へスナップする
- ダイヤル・数値・局一覧・前後スキャンの複数操作を許容する

#### 8.2.2 ステーション定義
各ステーションは以下を保持する。

- 基本情報: id, name, description, genre
- 周波数情報: frequencyMHz
- パーソナリティ情報: seed, personalityProfile, personalityGenVersion
- 編成情報: セグメント順序、比率、目標尺
- 音楽方針: ローカル音源ルール、AI音楽生成ルール
- レター方針: 採用条件、読み上げ形式、返信方針

### 8.3 セグメント

#### 8.3.1 セグメント種別
- TALK
- MUSIC_LOCAL
- MUSIC_AI
- JINGLE
- LETTER
- ANNOUNCEMENT（任意）

#### 8.3.2 MVP方針
- 20〜60秒程度の短尺セグメントを基本とする
- サーバーは次のN件を先読みする
- 生成済みアセットURLをクライアントへ配布する

### 8.4 台本生成

- トークとレター回答はLLMで生成する
- 台本には以下を反映する
  - ステーションの人格設定
  - セグメント種別
  - 目標尺
  - 直前文脈
  - 必要な入力情報（レター本文、トレンド要約など）
- 読み上げ用文体へ整形して返す

### 8.5 TTS

- 台本をTTSで音声化する
- 話者ID、速度、ピッチ等をステーションまたはパーソナリティに紐付ける
- サーバーは生成済み音声ファイルを管理し、クライアントに再生URLを返す

### 8.5 音声出力方式方針

#### 8.5.0 基本方針
音声出力は、次の2方式を両立可能な設計とする。

1. **Server-side TTS方式**
   - Serverが台本から音声ファイルを生成し、クライアントへ配信する
   - Webクライアントの基本方式とする

2. **Client-side TTS方式**
   - Serverが台本・読み・感情・話者指示を返し、クライアント側音声エンジンで合成する
   - 将来のC#ネイティブクライアント向け拡張方式とする

このため、パーソナリティ定義は **言語人格** と **音声エンジン依存設定** を完全に分離する。

### 8.5.1 日本語パーソナリティ方針

本システムにおける「パーソナリティ」は、単なるキャラクター設定ではなく、**日本語で自然に話すための言語設計 + 音声設計** の両方を含むものとする。

パーソナリティは少なくとも以下の2層に分離する。

1. **Language Persona**
   - 一人称、二人称
   - 敬体/常体
   - 語尾傾向
   - テンポ感
   - 相槌、間投詞
   - 感情温度（落ち着き / 明るさ / 熱量）
   - 話題バイアス
   - 禁則表現
   - レター回答時の態度

2. **Voice Persona**
   - TTSエンジン種別
   - speaker / style / preset
   - 話速、ピッチ、音量
   - 句読点や改行への反応特性
   - 感情表現パラメータ
   - server-side / client-side のどちらに対応するか
   - クライアント固有マッピングキー（将来のVOICEROID系アダプタ用）

この分離により、同じキャラクター設定に対して声だけ差し替える、または同じ声で複数の話し方を使い分ける運用を可能にする。

### 8.5.2 日本語パーソナリティ要件

#### 8.5.2.1 基本要件
- 既定ロケールは `ja-JP` とする
- 台本生成は「読まれる文章」であることを前提に、書き言葉ではなく話し言葉寄りで整形する
- レター回答、雑談、告知で口調テンプレートを切り替えられるようにする
- 句読点、三点リーダ、感嘆符の使い方を制御可能にする

#### 8.5.2.2 日本語品質要件
- 地名、人名、作品名、英数字混じり語の読み誤りを抑える
- 長すぎる一文を自動分割し、TTSに適した長さへ整形する
- 読みづらい記号列、URL、絵文字等は読み上げ向けに変換または省略する
- 放送禁止寄り語彙、過度に攻撃的な文体、説明責任を越える断定表現は抑制する

#### 8.5.2.3 話者設計要件
- パーソナリティごとに「落ち着いた深夜ラジオ系」「元気な朝番組系」「知的な解説系」などのアーキタイプを保持できるようにする
- 同一ステーション内でサブ話者を追加できる拡張余地を残す
- 将来の掛け合い対応を見据え、主話者/副話者の区別を持てるようにする

### 8.5.3 日本語TTSフレームワーク候補

#### A. VOICEVOX系
- HTTPサーバーとして利用でき、Javaサーバーから呼び出しやすい
- 日本語読み上げ用途で扱いやすく、ローカル運用しやすい
- MVPで最も導入しやすい候補

#### B. AivisSpeech系
- 日本語専用の音声合成エンジンとして扱いやすく、Style-Bert-VITS2 系モデルを利用できる
- よりキャラクター性や声質差の作り込みを狙う場合の有力候補

#### C. Style-Bert-VITS2系
- スタイル制御や独自音声づくりの自由度が高い
- 反面、運用難度とモデル管理難度は上がる

### 8.5.4 将来のC#クライアント連携方針

- C#クライアントは Server API に対して自クライアントの Capability を送信できるようにする
- Capability には少なくとも以下を含める
  - `supportsClientSideTts`
  - `supportedVoiceEngines`
  - `preferredPlaybackMode`
  - `localVoiceProfiles`
- Serverは Capability に応じて、音声ファイル返却か、読み上げスクリプト返却かを選択する
- C#クライアント側では、VOICEROID系など特定エンジンへの依存を **Client Adapter層** に閉じ込める
- Serverは特定ベンダーAPIへ直接依存せず、`SpeechDirective` 形式の中立メッセージを返す

#### SpeechDirective の想定要素
- `text`
- `normalizedText`
- `pronunciationHints`
- `emotion`
- `tempo`
- `pauseHints`
- `personaRef`
- `voiceHint`

これにより、Webクライアントは従来通り音声ファイル再生を行い、C#ネイティブクライアントは同じ番組情報を元にローカル音声エンジンで発話できるようにする。

### 8.5.5 MVPでの推奨方針

- **MVPの第一候補TTS** は VOICEVOX系
- **将来拡張候補** として AivisSpeech / Style-Bert-VITS2 系を許容
- 初期は「声の自然さ」よりも **安定再生・読み制御・導入容易性** を優先する
- 日本語パーソナリティは、最低でも以下の設定を持つ
  - `displayName`
  - `languageTone`
  - `firstPerson`
  - `sentenceStyle`
  - `phraseTraits`
  - `ngPolicy`
  - `voiceProfile`
  - `pronunciationDictionaryRef`

### 8.5.6 日本語辞書・正規化

- TTS前処理として、読み辞書とテキスト正規化を独立コンポーネントで持つ
- 固有名詞、作品名、英単語、数字、単位、日付の読み変換ルールを持つ
- 辞書はステーション共通辞書と局固有辞書の2段構成を許容する
- MusicGen由来の曲名、AI生成固有名詞、レター投稿者名の読みも補正対象とする

### 8.5.7 推奨内部コンポーネント追加

- `JapaneseScriptNormalizer`
- `PronunciationDictionaryService`
- `PersonaStyleResolver`
- `TtsVoiceRouter`
- `JapaneseQualityGuard`
- `ClientCapabilityResolver`
- `SpeechDirectiveAssembler`
- `NativeClientVoiceAdapterContract`

### 8.6 音楽生成AI

#### 8.6.1 目的
- トークの合間に差し込む楽曲やBGMをローカルAIで生成する
- ステーションのジャンルや雰囲気に合わせた独自曲を使えるようにする

#### 8.6.2 連携方式
- Javaサーバーは Music Generation Provider を通じてローカルAIへ要求を出す
- ローカルAIは別プロセス/別サービスとして動作してよい
- インターフェースは以下のいずれかを許容する
  - ローカルHTTP API
  - CLI起動 + ジョブ管理
  - キューファイル監視方式

#### 8.6.3 入力
- ジャンル/ムード/使用場面タグ
- 曲長
- 任意で歌詞
- シード
- 生成モード（番組BGM/インスト/歌あり など）

#### 8.6.4 出力
- 音声ファイル
- メタデータ（duration, prompt hash, provider, seed）

#### 8.6.5 失敗時挙動
- AI音楽生成に失敗しても再生を止めない
- 以下の優先順位で代替する
  1. キャッシュ済みAI生成音楽
  2. ローカル音源
  3. ジングル/SE
  4. トーク置換

### 8.7 プレイアウト

- サーバーが番組キューの正本を持つ
- キュー項目は talk / music_local / music_ai / jingle / letter を持つ
- クライアントはサーバーが提示した順序に従って再生する
- 局切替時は以下を行う
  - 現在キューの中断またはフェードアウト
  - 新局のコンテキスト構築
  - 先読み生成
  - 新キューの再配布

### 8.8 レター

#### 8.8.1 投稿
- 宛先局または共通宛を選択できる
- 入力項目は stationId / subject / body / radioName を基本とする

#### 8.8.2 管理
- 状態: UNREAD / PENDING / ADOPTED / REPLIED を基本とする
- ステーション別・状態別・キーワード検索を行える

#### 8.8.3 放送採用
- レターコーナーで採用済レターを優先的に処理する
- 読み上げ + AI回答 + 放送履歴記録を行う

#### 8.8.4 安全対策
- レター本文は引用データとして扱う
- システム命令や設定変更指示として解釈しない
- 個人情報や機密値を不要に出力しない

### 8.9 設定

- サーバー設定として以下を保持する
  - stations
  - providers.llm
  - providers.tts
  - providers.musicGen
  - playout
  - cache
  - paths
  - logging
- APIキー等は参照方式で保持し、直書きしない
- 設定のエクスポート/インポートを可能にする

### 8.10 キャッシュ

- script / tts audio / ai music を対象とする
- TTL、容量、削除ポリシーを設定可能とする
- キャッシュキーには provider fingerprint と input hash を含める

### 8.11 ログ / 監視

- 生成・再生・障害・リトライをサーバーログへ出力する
- correlationId で一連の処理を追跡可能にする
- 少なくとも以下の状態を画面表示できるようにする
  - LLM接続状態
  - TTS接続状態
  - MusicGen接続状態
  - バッファ残量
  - 直近エラー

## 9. 非機能要件

### 9.1 可用性
- LLM/TTS/MusicGenの一部失敗でも全体再生は継続できること
- サーバー再起動後も設定・レター・履歴が維持されること

### 9.2 性能
- 局切替時は数秒以内に次再生が始まることを目標とする
- 再生途切れを防ぐため、先読みバッファを持つこと
- 音楽生成は高遅延を許容するが、番組再生に支障を与えないよう非同期ジョブ化する

### 9.3 保守性
- JavaサーバーとAI生成サービスを分離し、片方だけ更新しやすい構成にする
- Provider追加時に上位ロジックを大きく変えないこと

### 9.4 セキュリティ
- ローカル用途前提でも、設定機密値は保護する
- 不要な外部公開を避ける
- 管理系APIは最低限保護する

### 9.5 監査性
- どの局で、どのセグメントが、どのProviderを使って生成されたかを追跡できること
