## 4. 主な設計差分と根拠

### 4.1 設定反映は第一段まで完了したが非同期深さと runtime profile が残る

- `SettingsService` と `SettingsDocument` の `playout` は `RadioService` の warmup/refill で参照されるようになった
- ready count, minimum ready duration, max prepared duration, max prepared blocks は runtime へ反映される
- 一方で `scriptAheadCount`, `ttsAheadCount`, `musicAheadCount` と `preGeneration` / `replay` / `composition` の runtime 反映は未着手である

### 4.2 runtime profile は API 契約までで止まっている

- `station_programming_policy` へ `pre_generation_policy`, `replay_policy`, `composition_policy` を保存できる
- ただし queue planning に `broadcast_archive`, replay share, composition balance を反映する実体がまだない
- `doc/13` の編成制御は編集 UI 向けの保存先まで先行し、runtime への反映が未完である

### 4.3 TALK / LETTER の本線が placeholder のまま

- `AssetService` は TTS provider として `PlaceholderTtsProvider` を注入し、queue item へ無音 WAV を生成している
- `SpeechDirectiveAssembler` も queue item title と station/persona から簡易文を組み立てるだけで、script asset snapshot を使っていない
- `doc/06` と `doc/08` の `Script -> Normalize -> TTS -> Asset` 本線が未着手である

### 4.4 MusicGen は server-worker 契約だけ成立している

- `MusicGenWorkerGateway` と `MusicGenerationRuntimeService` により `submit -> poll -> generated_asset` は動く
- ただし worker 内部は `workers/musicgen/app/main.py` の deterministic WAV 生成であり、実モデル adapter がない
- 障害時も queue を縮退継続させる実音源 fallback は未実装で、現状は `FAILED` + `DEGRADED` に寄っている

### 4.5 cache lifecycle は着手済みだが archive と eviction job が残る

- `generated_asset` は `byte_size`, `reuse_scope`, `reuse_count`, `last_accessed_at`, `expires_at`, `archive_eligible` を保持できるようになった
- asset 読み出しと clone 時の access 更新も最低限は入った
- `broadcast_archive` テーブル、archive promotion job、replay 参照ロジック、eviction job は未実装である

### 4.6 Web は骨格ができたが機能完結と observability / QA の仕上げが残る

- `/web` が追加され、`/`, `/letters`, `/settings`, `/monitor` の初期画面と API client, SSE 基盤は実装済みである
- client 側の `Last-Event-ID`, 指数バックオフ, `subtitle.updated` 受信処理は実装済みである
- 一方で `/letters` の利用者向け「自分が送ったレター一覧 / 採用履歴」、`/settings` の編集 UI、`/monitor` の recent errors / jobs / audit events、UI test は未実装である
- `.github/workflows/ci.yml` は依然として `unit` と `docker` の 2 job のみで、Web / worker 専用 job がない

### 4.7 2026-04-02 再点検で見つかった実装ズレ

- `LiveStreamBridge` は `lastEventId` を state に保存しつつ `useEffect` の依存配列にも含めているため、イベント受信のたびに購読を張り直す構造になっている
- `/letters` は公開投稿画面と管理 inbox を 1 画面へ混在させており、`doc/03` の「自分が送ったレターの簡易一覧 / 放送採用履歴」とは役割がずれている
- レター投稿 API は server 側で `Idempotency-Key` を受け付けるが、Web client は未送信で二重投稿防止が UI 側へ接続されていない
- `AppFrame` は管理トークン有無に関係なく `/settings` と `/monitor` を常時表示しており、`doc/03` の管理導線条件とずれている
- 字幕表示には `aria-live="polite"` が付いておらず、スクリーンリーダー向け更新導線が未達である
- `AudioConsole` コンポーネントは存在するが未接続で、音量反映と `PLAYBACK_STOPPED` 通知を持つ実装がラジオ画面へ取り込まれていない

### 4.8 2026-04-03 フォローアップ

- `LiveStreamBridge` は `lastEventId` の ref 保持へ切り替え、イベント受信ごとの再購読ループを解消した
- `AppFrame` は管理トークン未設定時に `/settings` と `/monitor` を隠し、字幕表示へ `aria-live="polite"` と `role="status"` を追加した
- `RadioDashboard` は `AudioConsole` を組み込み、`POST /api/radio/playback-events` の必須項目 `clientId`, `occurredAt` を含めて送信するようにした。item 切替時は前の音声を停止して状態をリセットする
- `/letters` は公開投稿カードと管理 inbox を分離し、公開投稿に `Idempotency-Key` を付けるようにした。管理トークン未設定時は一覧・採用・返信・履歴を表示しない
- Server は `subtitle.updated` の `SubtitlePayload` を配信し、再生中 item の字幕更新と停止時クリアを SSE で通知するようにした
- なお、公開側の「自分が送ったレターの簡易一覧 / 放送採用履歴」と、`/monitor` の recent errors / jobs / audit events は引き続き未実装である

## 5. 詳細実装タスク

### 5.1 Phase A: Server runtime を設計値へ寄せる

目的:

- 設定 API と queue/planning runtime の乖離をなくす
- Web 実装前に Server の挙動を設計どおり固定する

タスク:

1. `A-01` `RadioService` の固定 ready/buffer 閾値を `SettingsDocument.playout` 参照へ置き換える
2. `A-02` `QueuePreparationPolicy` 相当の service を追加し、`targetReadyCount`, `minimumReadyCount`, `minReadyDurationMs`, `maxPreparedDurationMs`, `maxPreparedBlocks` を集中管理する
3. `A-03` `scriptAheadCount`, `ttsAheadCount`, `musicAheadCount` を使って非同期生成深さを segment type ごとに制御する
4. `A-04` `ProgrammingService` に `preGeneration` / `replay` / `composition` を runtime 適用する読み出し層を追加する
5. `A-05` provider health, pending letters, template slot の `fallbackSegmentTypes` を queue 生成時に統合評価する
6. `A-06` `LEGACY_RATIO` fallback を常用経路から退避させ、設計上の最終 fallback に限定する
7. `A-07` `RadioServiceStateMachineTests` と service test を拡張し、設定変更で挙動が変わることを検証する

完了条件:

- `/api/settings` の playout 値を変更すると warmup/refill 挙動が変わる
- queue planner が runtime profile を参照して segment 構成を変える

2026-04-02 実装状況:

- `RadioServiceStateMachineTests` に設定値反映の回帰 test を追加した
