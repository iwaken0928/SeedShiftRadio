# パイプライン・コンテナデプロイ仕様書

## 1. 目的

本書は SeedShiftRadio を GitLab CI/CD から同一サーバー上の Podman Compose 環境へデプロイするための仕様を定義する。対象は Spring Boot Server と Next.js Web であり、PostgreSQL は compose 内で起動せず、デプロイ先ホスト上の既存 PostgreSQL を正本として利用する。

## 2. 前提

- CI/CD の正本は `.gitlab-ci.yml`
- デプロイはデプロイ先サーバー上の GitLab Runner で実行する
- コンテナ操作は `podman --remote` と `podman --remote compose` を使う
- Server / Web image は GitLab Container Registry へ push する
- PostgreSQL は同一ホストの `127.0.0.1:5432` を標準接続先にする
- Web は host network で `0.0.0.0:3000` を直接公開する
- Server は host network で起動し、標準では `127.0.0.1:8080` に bind する

## 3. Pipeline stages

| stage | 主な job | 役割 |
|---|---|---|
| `validate` | `ci-yaml-validate`, `compose-prod-validate` | CI YAML と production compose の構文確認 |
| `test` | `server-unit`, `api-contract`, `server-docker`, `web-typecheck`, `web-unit`, `web-e2e`, `worker-contract` | server unit、OpenAPI / 認証 / 設計書契約、Testcontainers、web、worker の回帰確認 |
| `build` | `server-container-build`, `web-container-build` | production image の build 確認 |
| `publish` | `server-container-publish`, `web-container-publish` | commit SHA / branch tag の image 作成。registry 設定時のみ push |
| `migrate` | `deploy-migrate` | deploy 前に既存 PostgreSQL へ Flyway migration を適用 |
| `deploy` | `deploy-app`, `deploy-musicgen`, 将来 `deploy-irodori-tts` | Podman Compose で Server / Web を更新起動。registry 未設定時は pull を省略。必要時は MusicGen worker や Irodori-TTS-Server を単独更新 |
| `smoke` | `smoke-production` | 公開 health、Web、管理 session、CSRF、認証済み管理 API proxy の確認 |
| `docs-check` | `pipeline-docs-check` | pipeline 仕様 document と関連設計書の参照確認 |

`deploy-migrate` と `deploy-app` は `main` ブランチ限定かつ manual 実行とする。`smoke-production` は `deploy-app` 成功後に自動実行する。

## 4. Image tags

- Build stage local tag: `localhost/seedshift-radio/server:$CI_COMMIT_SHORT_SHA`, `localhost/seedshift-radio/web:$CI_COMMIT_SHORT_SHA`
- Publish / deploy repository: `SEEDSHIFT_IMAGE_REPOSITORY` があれば優先し、未設定なら `CI_REGISTRY_IMAGE` を使う
- Server commit tag: `<repository>/server:$CI_COMMIT_SHORT_SHA`
- Server branch tag: `<repository>/server:$CI_COMMIT_REF_SLUG`
- Web commit tag: `<repository>/web:$CI_COMMIT_SHORT_SHA`
- Web branch tag: `<repository>/web:$CI_COMMIT_REF_SLUG`

GitLab Container Registry が無効などの理由で `CI_REGISTRY_IMAGE` が空になる環境では、`SEEDSHIFT_IMAGE_REPOSITORY` は `localhost/seedshift-radio` に fallback する。この場合 `publish` job は registry push を行わず、同一 Podman 環境の local image を deploy に使う。外部 registry へ push したい場合だけ、GitLab CI/CD Variables に `SEEDSHIFT_IMAGE_REPOSITORY` と `CI_REGISTRY` / `CI_REGISTRY_USER` / `CI_REGISTRY_PASSWORD` を設定する。デプロイは commit tag を使用する。rollback は直前成功 commit tag を `SEEDSHIFT_SERVER_IMAGE` / `SEEDSHIFT_WEB_IMAGE` に戻し、同じ compose file で `podman --remote compose up -d` を再実行する。

## 5. Container 構成

Production compose の正本は `infra/compose/compose.prod.yml` とする。

- `server`
  - image: `SEEDSHIFT_SERVER_IMAGE`
  - `network_mode: host`
  - DB 接続: `SEEDSHIFT_RADIO_DB_HOST=127.0.0.1`, `SEEDSHIFT_RADIO_DB_PORT=5432`
  - bind: `SERVER_ADDRESS=127.0.0.1`, `SEEDSHIFT_RADIO_SERVER_PORT=8080`
  - data: 既定では Podman managed volume `seedshift-radio-data` を `/var/lib/seedshift-radio` へ mount

- `web`
  - image: `SEEDSHIFT_WEB_IMAGE`
  - `network_mode: host`
  - bind: `HOSTNAME=0.0.0.0`, `PORT=3000`
  - browser API base: same-origin `/api-proxy` 固定
  - internal proxy target: `SERVER_INTERNAL_API_BASE_URL=http://127.0.0.1:8080`
  - server-side secrets: `SEEDSHIFT_ADMIN_TOKEN`, `SEEDSHIFT_WEB_ADMIN_PASSWORD`, `SEEDSHIFT_WEB_SESSION_SECRET`

Web は `/api-proxy/:path*` を Next.js Route Handler で Server の `/:path*` へ中継する。ブラウザからは `http://<server-host>:3000/` の same-origin 通信になり、Server の CORS を広げずに `/api/*` と SSE を利用できる。

管理者は `POST /api/auth/login` へ管理 UI 用パスワードを送信し、署名済み `seedshift_admin_session` cookie を確立する。cookie は `HttpOnly`, `SameSite=Strict` とし、production では `Secure` を付ける。`GET /api/auth/session` は認証状態と CSRF token を返し、unsafe な管理操作と logout は `X-CSRF-Token` を要求する。未認証の管理 API proxy は `401`、CSRF 不正は `403` で拒否する。

`SEEDSHIFT_ADMIN_TOKEN` は Web の server-side Route Handler が認証済み管理リクエストを Server へ中継する時だけ `X-Admin-Token` として注入する。`SEEDSHIFT_WEB_ADMIN_PASSWORD` と `SEEDSHIFT_WEB_SESSION_SECRET` も Web process の実行時環境変数に限定する。これらを `NEXT_PUBLIC_*`、browser bundle、Cookie payload、localStorage、画面、標準ログへ出さない。

- `musicgen`
  - job: `deploy-musicgen`
  - image: `MUSICGEN_IMAGE_NAME`（既定: `localhost/seedshift-radio/musicgen:$CI_COMMIT_SHORT_SHA`）
  - bind: `MUSICGEN_HOST_BIND=0.0.0.0`, `MUSICGEN_HOST_PORT=28080`
  - data: `MUSICGEN_DATA_VOLUME` が設定されている場合だけ `/data` へ `:Z` 付きで mount する。未設定時は container-local の一時領域を使う

`MUSICGEN_DATA_VOLUME` は Podman managed volume 名または絶対 host path を指定できる。host path を使う場合は、deploy 前に directory、所有者、権限、backup 方針を Runner host 側で準備する。

- `irodori-tts`
  - job: 将来 `deploy-irodori-tts`
  - image: `IRODORI_TTS_IMAGE_NAME`（既定候補: `localhost/seedshift-radio/irodori-tts:latest` または upstream Dockerfile build）
  - bind: `IRODORI_TTS_HOST_BIND=127.0.0.1`, `IRODORI_TTS_HOST_PORT=8088`
  - model: 既定は `Aratako/Irodori-TTS-500M-v3`
  - voices: `IRODORI_TTS_VOICES_VOLUME` を container の `voices/` へ mount
  - cache/model volume: Hugging Face cache 用に `IRODORI_TTS_MODEL_VOLUME` を mount し、container 再作成時の再ダウンロードを避ける
  - GPU: NVIDIA GPU がある環境では GPU compose override または `podman --remote run --device nvidia.com/gpu=all --security-opt=label=disable ...` を使う

Irodori-TTS-Server は OpenAI互換 API を提供するが、SeedShiftRadio の外部公開 API として直接公開しない。標準 bind は `127.0.0.1` とし、外部 bind が必要な場合は bearer token、firewall、許可元制限を必須にする。参照音声 volume には同意済みファイルのみを置き、deploy log へ voice file 名や個人名を過剰に出さない。

## 6. Migration

`deploy-migrate` は published Server image を使い、host network で既存 PostgreSQL に接続する。実行時は `SPRING_MAIN_WEB_APPLICATION_TYPE=none`, `SEEDSHIFT_RADIO_MIGRATION_ONLY=true`, `SEEDSHIFT_RADIO_JOBRUNR_ENABLED=false`, `JOBRUNR_JOB_SCHEDULER_ENABLED=false` を指定し、Web server と background job を起動せずに Spring Boot 初期化時の Flyway migration を適用する。`SEEDSHIFT_RADIO_MIGRATION_ONLY=true` の場合、Spring 初期化と migration の成功後に ApplicationContext を close し、container process を exit code 0 で終了させる。

Migration が失敗した場合、`deploy-app` は実行しない。DB 接続先、ユーザー権限、Flyway validation error を確認してから再実行する。

必須:

- `SEEDSHIFT_RADIO_DB_PASSWORD`
- `SEEDSHIFT_ADMIN_TOKEN`
- `SEEDSHIFT_WEB_ADMIN_PASSWORD`

推奨:

- `SEEDSHIFT_DEPLOY_DIR`
- `SEEDSHIFT_RADIO_DATA_VOLUME`
- `SEEDSHIFT_RADIO_DB_HOST`
- `SEEDSHIFT_RADIO_DB_PORT`
- `SEEDSHIFT_RADIO_SERVER_PORT`
- `SEEDSHIFT_WEB_PORT`
- `SEEDSHIFT_SMOKE_API_BASE_URL`
- `SEEDSHIFT_SMOKE_WEB_BASE_URL`
- `SEEDSHIFT_SMOKE_WEB_API_PROXY_BASE_URL`
- `MUSICGEN_HOST_BIND`
- `MUSICGEN_HOST_PORT`
- `MUSICGEN_IMAGE_NAME`
- `MUSICGEN_DATA_VOLUME`
- `IRODORI_TTS_HOST_BIND`
- `IRODORI_TTS_HOST_PORT`
- `IRODORI_TTS_IMAGE_NAME`
- `IRODORI_TTS_VOICES_VOLUME`
- `IRODORI_TTS_MODEL_VOLUME`
- `IRODORI_TTS_API_KEY`

秘密値は GitLab の masked / protected variable として登録し、リポジトリへ実値を置かない。Runner 上に生成される deploy `.env` は `umask 077` で作成する。
`SEEDSHIFT_WEB_SESSION_SECRET` は UTF-8 で 32 byte 以上の高エントロピーなランダム値を使い、変更すると既存管理 session がすべて無効になるものとして計画する。

## 8. 初回デプロイ前チェック

- PostgreSQL が `127.0.0.1:5432` で listen している
- DB、ユーザー、パスワード、migration 権限が用意されている
- GitLab Runner ユーザーが `podman --remote`, `podman --remote compose`, registry pull, deploy directory 書き込みを実行できる
- `SEEDSHIFT_RADIO_DATA_VOLUME` の `config/` が作成可能
- `MUSICGEN_DATA_VOLUME` に host path を指定する場合は、`/data` として書き込める directory と backup 方針が準備済み
- Irodori-TTS を使う場合は NVIDIA GPU / CPU fallback の所要時間、`voices/` の参照音声同意、model cache volume、`127.0.0.1:8088` の bind、optional bearer token が準備済み
- host firewall が Web 公開 port `3000` を許可している
- Server API を外部公開しない場合、`8080` は host 内部または許可元限定のままにする
- `SEEDSHIFT_WEB_ADMIN_PASSWORD` と `SEEDSHIFT_WEB_SESSION_SECRET` が masked / protected variable として登録済み
- TLS 終端後の HTTPS で Web を利用し、production の `Secure` session cookie を送信できる

## 9. Smoke test

`smoke-production` は deploy runner host から以下を確認する。

- `GET ${SEEDSHIFT_SMOKE_API_BASE_URL}/api/health`
- `GET ${SEEDSHIFT_SMOKE_WEB_BASE_URL}/`
- `GET ${SEEDSHIFT_SMOKE_WEB_API_PROXY_BASE_URL}/api/health`
- 未認証 `GET ${SEEDSHIFT_SMOKE_WEB_BASE_URL}/api-proxy/api/settings` が `401`
- `POST ${SEEDSHIFT_SMOKE_WEB_BASE_URL}/api/auth/login` で session cookie を発行
- 認証済み `GET ${SEEDSHIFT_SMOKE_WEB_BASE_URL}/api-proxy/api/settings` が成功
- 不正な CSRF token の logout が `403`、正しい CSRF token の logout が `204`
- logout 後の `GET ${SEEDSHIFT_SMOKE_WEB_BASE_URL}/api/auth/session` が未認証

認証 smoke は `scripts/smoke-admin-session.sh` を使い、production では session cookie の `Secure` 属性も検査する。Runner 内部の HTTP loopback では取得済み cookie を明示して BFF 契約を検査するが、利用者経路は TLS 終端後の HTTPS を必須とする。管理 UI 用パスワードや CSRF token は標準出力へ表示しない。Server 管理トークンは Web process 内だけで注入され、smoke client へ渡さない。
- `podman --remote ps` で Server / Web container が起動中
- Irodori-TTS を有効化した構成では `GET http://127.0.0.1:${IRODORI_TTS_HOST_PORT}/health` と `/v1/models` を確認し、実音声生成 smoke は手動または GPU smoke に分離する

失敗時は該当 container の `podman --remote logs`、PostgreSQL 接続情報、deploy `.env` の image tag、firewall を確認する。ログ確認では `radioName`, letter body, prompt, API key, 管理トークン, DB password を貼り付けない。

## 10. Rollback

1. 直前成功 pipeline の Server / Web commit tag を確認する
2. deploy runner 上の deploy `.env` で `SEEDSHIFT_SERVER_IMAGE` と `SEEDSHIFT_WEB_IMAGE` を直前成功 tag に戻す
3. `podman --remote compose --env-file <deploy-dir>/.env -f <deploy-dir>/compose.yml pull`
4. `podman --remote compose --env-file <deploy-dir>/.env -f <deploy-dir>/compose.yml up -d`
5. `smoke-production` と同じ URL を確認する

DB migration 後の rollback はスキーマ後方互換を前提にする。破壊的 migration が必要な場合は事前に backup / restore 手順を別途用意し、本 pipeline だけで巻き戻した扱いにしない。
